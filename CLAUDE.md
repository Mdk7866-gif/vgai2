# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

**vgAI** is an AI video-production SaaS: creators paste a script, split it into scenes, and generate matching images/animations/voiceovers per scene, reusing saved character and style-template libraries. Full product spec (all pages, features, and the credit system) is in [`README.md`](./README.md) — read it before implementing any feature, it's the source of truth for intended behavior. The full DB schema is in [`vgaidatabase.dbml`](./vgaidatabase.dbml).

**Current state: early build, not just scaffold anymore.** Auth (Supabase Google OAuth, an inline `LoginModal` gating write actions rather than a forced login redirect) and three full CRUD library features are implemented end-to-end, backend route + Pydantic schema + frontend page/card/edit-popup: **Characters** (`/characters`), **Style Templates** (`/style_templates`), and **Generate Scripts** (`/generate_script`, `script_templates` + `researched_topics` + `generated_scripts`). Characters and Style Templates each have their "Generate with AI" flow fully built (see AI-generation pattern below) — **not Gemini as originally spec'd in `README.md`**, both use OpenAI (LangChain `ChatOpenAI` for text/structured output, `gpt-image-2` for character sheet images) via `app/openai_client.py`. Style Templates' create/edit form and its "Generate with AI" flow are both aspect-ratio-aware (`16:9` long-video vs `9:16` Reels, a single picker driving both `image_aspect_ratio`/`video_aspect_ratio` and, on the generate path, a distinct system-prompt creative brief per format — see AI-generation pattern below). `/style_templates` also shows a **Starter Templates** catalog of 12 product-default styles — served read-only from the shared `default_style_templates` table (not seeded rows, and **no longer a bundled JSON file** — that's gone; the catalog is edited from the vgai2admin portal), browsable in one big popup and importable into the user's library with one click. `/characters` has the same thing (**Starter Characters**, `default_characters`). See the two starter-catalog bullets below. Style templates additionally carry two optional Advanced-Settings fields, `best_for` and `demo_image_url`. `/generate_script` is a different, multi-step AI flow — research 10 viral topics (Perplexity `perplexity/sonar-pro`) → generate a full script + character list per chosen topic (Claude `anthropic/claude-sonnet-5`) → optional feedback-driven "Improvise" regeneration, all fully DB-backed and persisted (see `/generate_script` AI pattern below) — unlike Characters/Style Templates' accept-or-reject-into-`create` pattern, research/generation here writes to the DB immediately as it happens, with no separate save step; only the reusable form-input preset (`script_templates`, gated by `is_saved`) still needs an explicit "Save as Template" click. Generated-script cards support inline edit and delete, and the "Import" button creates a new `/project_folder/{project_id}` project pre-filled with that script (see below) rather than being a placeholder. `/liked_projects` is also implemented — liking is a `projects.is_liked` toggle reachable from the sidebar (heart icon per project row), shown as a card grid via `LikedProjectsCard.tsx`, and kept in sync everywhere through the shared `ProjectsContext` (see Frontend architecture below) rather than a separate fetch per page. Credit top-ups are also implemented end-to-end via Razorpay (`app/routes/payments/crud.py` — order creation + Checkout-signature verification; `app/routes/payments/webhook.py` is a documented, not-yet-registered backup path, see its docstring). **`/profile` is now fully built too** — the account header plus a two-tab history card (`PaymentAndUsageHistoryTabCard.tsx`) covering README §`/profile`'s Payment History and Usage History, backed by `GET /payments/history` and `GET /profile/usage-history` (see both architecture sections below). The Navbar's credit-balance pill is live app-wide via a shared `CreditBalanceContext` (see Frontend architecture below) — spending credits anywhere updates it instantly, not just on next page load. Navbar and Sidebar are real chrome (not placeholders — see Frontend architecture below). **`/contact` is built** (a real support form — name / email-or-mobile / description / optional screenshot, usable signed-out; see the Contact form bullet below), and so is **`/privacy-policy`** (a full 13-section static policy page, no backend). **`/about` is still a "coming soon" placeholder page** — a real route rendering a stub, the one such placeholder left. The home page (`/`) also still has leftover demo-popup buttons (Interactive Components section) from the original template — not a real feature, safe to delete when that section of the app gets built. Don't assume a feature exists in code just because it's documented in `README.md`; check the actual route/component first. (`README.md` used to name Gemini for the Characters/Style Templates flows; that has since been corrected there, but the general rule stands — the spec is intent, this file tracks what's real.)

**`/project_folder/{project_id}` — also now built, but only its first slice.** Project-folder CRUD is wired from the sidebar (`Sidebar.tsx`'s Project Folders section — create/rename/delete, live everywhere via `ProjectsContext`) and the workspace page itself (`app/(app)/project_folder/[project_id]/page.tsx`) supports: pasting/autosaving a script, importing characters/a style template (`ChooseCharacterPopUp.tsx`/`ChooseStyleTemplatePopUp.tsx`, snapshotted the same way `POST /projects/create` auto-imports the user's default character(s)/style template on project creation), saving ElevenLabs voiceover *settings* (`VoiceOverControllerPopUp.tsx` — settings only, no TTS call yet), picking `llm_model_id`/`image_model_id`/`animation_model_id` tiers (`AdvancedSettingsPopUp.tsx`), and **"Generate Scenes (Automatic)"** — a single structured LLM call (`app/routes/project/paidscripttoscenesplitter.py`, `gpt-4o` for `"base"`/`gemini-3-pro-preview` for `"pro"` via `app/gemini_client.py`) that replaces the project's scene batch outright and writes video metadata (title/description/tags/thumbnail prompt) onto the `projects` row. Each `SceneCard.tsx` can then generate its own image (`app/routes/project/imagegeneration.py`, `gpt-image-2`, multi-image `images.edit` reference call when the scene has involved characters) and, once an image exists, its animation (`app/routes/project/animationgeneration.py`, `alibaba/wan-2.6` for `"base"`/`google/veo-3.1-lite` for `"pro"` via OpenRouter's video API, `app/openrouter_video.py`'s long-running-job polling) — and `VideoMetaDataCard.tsx` can generate the video thumbnail the same way. **"Generate Scenes (Manual)" is now wired too** — `app/routes/project/freescripttoscenesplitter.py` (`POST /projects/scenes/generate_manual`, registered in `router.py`) is the free/manual counterpart to `paidscripttoscenesplitter.py`: no LLM call happens server-side, the user copies a prompt built client-side by `GenerateScenesManualPopUp.tsx`, runs it through gemini.com themselves, and pastes back the structured JSON response, which the backend parses defensively (code-fence stripping, same style as `viralscripttopicresearch.py`'s Perplexity parser) and validates against the same `SceneSplitDraft` shape the automatic flow's LLM call produces — both flows now share their scene-persistence logic (replace-batch, write video metadata) via `app/routes/project/scenesplitcommon.py`, which also holds `WORDS_PER_CREDIT_AUTO`/`WORDS_PER_CREDIT_MANUAL` and the two response schemas were unified into one `GenerateScenesResponse` (`app/schemas/scene.py`) since both endpoints return the same shape. Manual is priced at `WORDS_PER_CREDIT_MANUAL = 100` vs automatic's `WORDS_PER_CREDIT_AUTO = 10` — 10x cheaper per word since no provider is billed on that path, though credits are still reserved (same `reserve_project_credits` shape) since parsing/persisting is still real backend work. **That charge happens on the trigger button click, not on paste-back** — a second endpoint, `POST /projects/scenes/generate_manual_charge`, reserves the credits before `GenerateScenesManualPopUp.tsx` opens and reveals the copy-paste prompt, and `/generate_manual` itself is then free (`credits_spent: 0`). Charging at paste-back only works if the paste-back is guaranteed to happen, and it isn't: the popup's whole value is the prompt it hands over, so a user could open it, copy the prompt, run the split on gemini.com, and generate images/animations elsewhere without ever pasting anything back. Same reasoning and same shape as `POST /projects/image/generate_manual` below. A side benefit: a malformed paste (or just retrying one) now costs nothing extra, since the charge already landed. **Scene-image generation now has a manual counterpart and a bulk "generate everything" mode alongside the existing per-scene automatic flow.** "Generate All Images (Manual)" opens `ManualImageGenerationPromptCopyPopUp.tsx` — a pure copy-paste tool (character-sheet-image copy buttons + batched scene-prompt copy buttons for pasting into meta.ai yourself) with no paste-back step, since there's no structured response to parse for images the way there is for a manual scene split. Its cost — `ceil(scene_count / SCENES_PER_CREDIT_MANUAL)`, `SCENES_PER_CREDIT_MANUAL = 5` in `imagegeneration.py` — is charged up front by `POST /projects/image/generate_manual` the instant the trigger button is clicked, before the popup even opens, since there's no later "generate" step to hang the charge on. "Generate All Images (Automatic)" is the bulk counterpart of `SceneCard.tsx`'s own per-scene Generate button: it walks every scene missing a `generated_image_url`, in batches of 5 concurrent requests, pausing 10s between batches (60s every 50 images) to avoid tripping the image provider's rate limit, live-updating a progress bar seeded from the project's already-generated count (not from zero) and showing the current batch number and any active cooldown countdown. Both this bulk button and every individual `SceneCard` Generate button draw from one page-owned pool of 5 concurrency slots (`tryAcquireImageSlot`/`releaseImageSlot` in `page.tsx`, threaded into `SceneCard` as props rather than context since only these two call sites need it) — a click that would exceed 5 concurrent generations is rejected with an `AlertMessagePopUp` warning instead of queueing silently. Stopping a bulk run aborts every in-flight request via `AbortController` *and* calls `POST /projects/scenes/cancel_generation` for each (mirroring `SceneCard`'s own Cancel button) so an abandoned generation doesn't keep running server-side and save after the user gave up on it; already-reserved credits for anything that had started are not refunded, consistent with the reserve-first model. Five consecutive failures auto-stops the run and surfaces every collected error in one alert, on the assumption that's a systemic problem (bad key, exhausted quota) rather than one-off bad luck. **"Download All" next to these two buttons is now built** — see the "Download All" bullet under Frontend architecture below (`lib/zip.ts`, `lib/downloadProject.ts`); it pulls every generated scene image/animation plus the thumbnail into a folder the user picks (File System Access API) or a `.zip` fallback, and costs nothing. **"Generate Voiceover" remains deliberately unwired** — visible as a disabled button on the page, its backend file (`app/routes/project/voiceovertts.py`) exists as an empty stub, not yet registered in `router.py`. **Each `SceneCard` also now supports manually uploading (click or drag-and-drop) an image/animation produced outside vgAI straight onto a scene**, plus deleting either asset outright — both free, no AI call, no credit cost (`generatedscenecard.py`'s `upload_scene_image`/`upload_scene_animation`/`delete_scene_image`/`delete_scene_animation`). Dropping/picking a replacement for an asset that already exists is gated behind an `AlertMessagePopUp` warning that the current one is being permanently deleted (Cloudinary included) before the upload proceeds. **Clicking "Regenerate" on a scene that already has an image no longer resubmits the same prompt that produced a disliked result** — `app/routes/project/imageregeneration.py`'s `POST /projects/image/regenerate_and_save` first has an LLM rewrite both the image and animation prompts (a fresh variation that preserves the established style), saves them, then generates from the rewritten image prompt; total cost is 1 credit for the rewrite plus the normal per-tier image-generation cost. Separately, hand-editing just the image prompt (without regenerating) offers — via a `ConformationMessagePopUp`, not automatically — to rewrite the animation prompt to match for 1 credit (`POST /projects/image/sync_animation_prompt`); declining leaves the animation prompt untouched. See the Backend/Frontend architecture bullets below for the actual patterns, which diverge from `README.md`'s original single-Gemini-call description of automatic scene generation.

## Commands

> **Ports 8000/3000 belong to this app. The sibling admin portal (`vgai2admin`)
> runs on 8001/3001 — keep it that way.** Both projects were on 8000/3000 once
> and it broke vgAI: Windows lets two processes bind the same port without an
> error, so vgai2admin's backend silently answered this app's requests. Its
> router only serves `/admin/*`, so `/users/me`, `/users/sync`, `/payments/...`
> all returned `{"detail":"Not Found"}` — users signed in fine (Supabase auth is
> client-side) into a completely dead app. **`app/access_control.py` stopped
> being enforced at the same time**, since `get_current_user` was never reached:
> restricted emails got a 404 instead of the 403 `ACCESS_REVOKED` that
> `AuthContext` signs people out on, so blocked users appeared to have access.
> If vgAI ever returns a bare "Not Found" for everything, check what is actually
> listening on 8000 before debugging anything else. See `vgai2admin/README.md` §10.3.

`awsdeployment.md` is the full runbook — **read it before answering any deployment question**, rather than reasoning from the compose file alone. The short version of what shapes everything else: four containers (nginx / backend / frontend / certbot); **only nginx publishes ports** (80/443), with backend and frontend `expose`-only on the internal network, so 3000/8000 must never be opened in the EC2 security group; everything is served from **one origin** (`/` → frontend, `/api/` → backend, prefix stripped by the trailing slash on `proxy_pass`), which is why the frontend calls the backend at the **relative** `/api` and no domain is compiled into its bundle; and the domain lives in exactly one place, `DOMAIN` in the root `.env`, from which nginx's `server_name`/cert paths and the backend's `ALLOWED_ORIGINS` are both derived. `NEXT_PUBLIC_*` values are frontend **build args**, so changing one needs `docker compose build frontend`, not a restart. There is nothing to provision for data — Supabase and Cloudinary are already hosted, and the deployment points at the same shared project the local app uses.

## Backend architecture

- **Routing**: `app/main.py` creates the `FastAPI` app and mounts `app/routes/router.py`'s `api_router`, which aggregates per-resource routers (`app/routes/users.py`, `app/routes/characters/crud.py`, `app/routes/styletemplates/crud.py`, `app/routes/scriptgenerationtemplate/crud.py`, `app/routes/payments/crud.py`, `app/routes/project/*.py`). Multi-endpoint resources live in their own subpackage (`app/routes/<resource>/crud.py` + `generate<resource>.py`). Add new resources the same way, and register the router in `router.py`.
- **Credits are reserved before the provider call, never deducted after it** (`app/credits.py`): every paid endpoint calls `reserve_misc_credits()`/`reserve_project_credits()` *before* invoking the AI provider, and only calls the matching `refund_*` helper if that provider call raised. The provider bills us the moment work starts, so charging only on success meant eating the cost of anything a user cancelled. Two things are deliberately **not** refunded: a user cancelling mid-flight, and a result discarded as stale by the generation-token guard (see the `/project_folder` bullet). Both spend paths go through Postgres functions (`spend_credits`/`refund_credits`/`add_project_expense`, defined in `vgaidatabase.sql`, applied to an existing DB via `vgaidatabase_migration_credits.sql`) rather than a read-then-write in Python — a user can fire several generations at once from the scene grid, and separate `SELECT`-then-`UPDATE` round trips all read the same starting balance and lose all but the last write. `spend_credits` raises `INSUFFICIENT_CREDITS`, which `app/credits.py` turns into the 402; that guard is authoritative, and the balance is only re-read to fill in the error message. **Nothing works until the migration is applied** — every paid endpoint 500s on a missing function.
- **AI-generation pattern** (`characters/generatecharacter.py`, `styletemplates/generatetemplate.py`): both `POST .../generate` endpoints follow the same shape — reserve a fixed per-call cost against `miscellaneous_credit_spent` (402 if insufficient), call OpenAI, refund if that call raised, and return the generated draft *unsaved*. The frontend shows an accept/reject preview (`GenerateCharacterSheetPopUp.tsx`, `GenerateStyleTemplatePopUp.tsx`); accepting re-submits the (possibly-edited) draft to the resource's normal `POST .../create` endpoint — generation never writes to the DB directly. `generatetemplate.py` also hard-truncates every generated field to its word-count ceiling after the LLM call, since prompting for a limit isn't a guarantee and an over-limit draft would fail `EditStyleTemplateCardPopUp.tsx`'s own validation on save/edit — keep those ceilings numerically in sync if either side changes. `generatetemplate.py` also builds its system message per-call via `_build_system_message(aspect_ratio)`, injecting one of two `VIDEO_FORMAT_BRIEFS` (long-form vs Reels) so the chosen aspect ratio actually changes what the AI writes (pacing/hook style), not just the saved metadata — keep the frontend's `ASPECT_RATIO_OPTIONS` and this dict's keys in sync. Both use OpenAI via `app/openai_client.py` (LangChain `ChatOpenAI` for text/structured-output, `gpt-image-2` for character-sheet images, `quality="low"`/`"high"` gated behind a "Generate with Pro" toggle on the character flow) — not Gemini, despite `README.md`. The backend balance check is the authoritative guard, but both Generate popups also call a `refreshBalance()` helper right before submit (re-fetches `GET /users/me`, aborts client-side with an error if now insufficient) — the balance shown on popup-open can go stale if the user's credits changed elsewhere (another tab, a top-up) while it sat open, and this avoids the wasted round-trip of hitting `/generate` only to get a 402 back. `GenerateStyleTemplatePopUp.tsx` additionally has a "Generate demo image" toggle (default off) that raises the shown/charged cost from `GENERATE_CREDIT_COST` (2) to `2 + GENERATE_DEMO_IMAGE_CREDIT_COST` (6) — when on, `generatetemplate.py`'s `/generate` reserves that combined total in one call, builds the draft as usual, and then (still inside the same try/except, so a demo-image failure refunds the whole 6 rather than leaving the draft's own cost unrefunded) generates+uploads a demo image from the *freshly-generated* `draft.image_prompt` via `_generate_and_upload_demo_image()` — reusing `DEMO_IMAGE_FOLDER`/`DEMO_IMAGE_SIZES`/`GENERATE_DEMO_IMAGE_CREDIT_COST`/`_build_demo_image_prompt()` imported straight from `crud.py` rather than duplicating them, so all three ways a demo image can be produced (paste, upload, the Edit popup's standalone Generate button, and this toggle) share one prompt-building/size/cost definition. Unlike the rest of this draft (returned unsaved for review), the demo image is a real Cloudinary upload the moment `/generate` returns — `GenerateStyleTemplateResponse.demo_image_url` is already a URL, not base64, and `handleAccept()` passes it straight through to `POST /styletemplates/create`'s `demo_image_url` field; rejecting and retrying leaves that upload orphaned, same accepted tradeoff as `upload_demo_image`/`generate_demo_image`. No `best_for` is available at this point in the flow (this AI-draft path doesn't collect or generate that field), so the reused prompt-builder is called with `best_for=None`.
- **Starter style-template catalog** (`app/routes/styletemplates/defaults.py`): 12 product-default style templates served read-only from the shared `default_style_templates` table, deliberately **not** rows in `style_templates` and **not** seeded on signup. Seeding freezes each user's copies at signup, so an improved prompt never reaches an existing account and shipping one needs a backfill inserting 12 rows per user; a served catalog means an edit updates what everyone sees on their next visit. It's also the single place a copy is made, which is where the fingerprint mitigation below belongs. **The catalog used to be a bundled `default_style_templates.json` read through an `lru_cache`d loader — that file is gone.** It's edited from the separate **vgai2admin** portal now (`C:\Users\ASUS\OneDrive\Desktop\vgai2admin`, its own repo — see that repo's README §9 and `app/routes/defaultstyletemplates/crud.py`), which is *why* there's no cache here anymore either: an admin edit has to show up on the next request, not the next restart. Migrated 1:1 from the old JSON with a one-time seed script (verified field-for-field and in the same order before the JSON was deleted). `GET /styletemplates/defaults` filters `is_published = true` (an admin can draft an entry invisible to vgai2 until it's ready) and is **unauthenticated**, matching the "public browsing, gated actions" rule — the starter library is the most persuasive thing a signed-out visitor sees. `POST /styletemplates/defaults/{slug}/import` is gated, also filters `is_published = true` (a hidden draft must not be importable by guessing its slug), and takes *only* a slug: prompt bodies are read server-side from the catalog, never posted back, so a tampered payload can't smuggle in different content and a catalog edit applies to the next import with no frontend change. The copy is a real copy with no link back to its catalog entry (same rule as `project_characters`) — importing the same slug twice yields two independent templates. **`demo_image_url` is copied as a real Cloudinary asset**, not as a URL string: `_IMPORTABLE_FIELDS` deliberately excludes it and the import calls `copy_image_from_url()` into `<user_id>/style_templates/` instead, so an admin replacing or deleting a catalog entry can never blank the preview on every template already imported from it. That was added after the starter-character catalog forced the same reasoning; a one-time backfill converted the two production rows that still shared a catalog URL, and `crud.py`'s `_owns_demo_image()` stays as a guard for a pasted external URL or a row restored from an old backup. Also, and a user's *first-ever* template is marked `is_default` so `POST /projects/create`'s auto-import of the default style template works without them setting one manually. Every field is written to sit under `EditStyleTemplateCardPopUp.tsx`'s word ceilings (image 300 / animation 200 / description 150 / YouTube prompts 150) so an imported template opens cleanly in the edit form without tripping its own validation.
  - **Design notes for writing/editing a catalog entry** (carried over from the markdown source that used to hold this as prose, since JSON can't hold commentary): every `image_prompt`/`animation_prompt` should rotate shot scale and camera move between scenes, state lighting explicitly per scene (image models default to dark/moody when unstated), and end with a "no readable text/lettering/numbers/signage/logos" clause — fabricated text is what turns a stylised image into apparent archival material. Keep prompt language **model-agnostic**: plain descriptive English, no aspect flags, weights, `::` separators, or render-engine tokens, since the same prompt has to behave across GPT Image 2, Gemini, *and* a user pasting it into meta.ai by hand through the manual image-generation flow. Thumbnails should bias bright/high-contrast (Noir Mystery is the deliberate dark exception). `scene_density` should skew toward `high` for documentary/story/calm-listening formats, where held shots are both correct pacing and the cheapest, most drift-resistant setting for expensive styles (photoreal, 3D). **Fingerprint risk**: if many users run a catalog entry unmodified, their channels produce visually interchangeable output — a detectable pattern under policies that evaluate whole channels and flag template clones. Cheap mitigation, not yet built: nudge palette/lighting/one detail clause server-side in `import_default_style_template()` when a user imports, so two users picking the same starter don't ship identical-looking channels. Catalog gaps noted but not yet filled: no fourth "very high" density tier for long-form documentary (which wants ~40-60 words/scene, past what `high` covers), no Pixel Art / Dark Cartoon / Cyberpunk Neon styles, and no `9:16` variants of any of the 12 (would need vertical-framed camera moves and one density step down for short-form pacing).
- **Contact form** (`app/routes/contact/crud.py`): the one write endpoint in the app that takes **no auth dependency at all**, and that is the entire design. `/contact` is reachable signed-out like the rest of the browsable app; a user whose access was *revoked* is signed out the instant the backend rejects them and is exactly who most needs support; and someone who can't sign in at all still has to be able to report that. Putting it behind `get_current_user` would run `enforce_access()` and 403 the people the form exists for. It still attributes when it can: `_optional_user_id()` reads a Bearer token *if one happens to be present* and resolves it best-effort, treating a bad/expired token exactly like no token, so `user_id` is filled for a signed-in submitter and null otherwise. **It deliberately does not call `enforce_access()`** — don't "fix" that by routing it through the normal dependency. Screenshots go to a product-wide `contacts/` Cloudinary folder rather than `<user_id>/...`, since a signed-out submitter has no user folder. Nothing here reads submissions back; they're listed and triaged from the vgai2admin portal (that repo's README §9.2), so there is no per-user "my tickets" endpoint to add.
- **Starter character catalog** (`app/routes/characters/defaults.py`): the character-library counterpart of the style-template catalog above, added later and built to the same rules — product-default characters served read-only from the shared `default_characters` table, deliberately **not** rows in `characters` and **not** seeded on signup, edited from the **vgai2admin** portal (`/defaultcharacter`, `app/routes/defaultcharacters/crud.py` there), with no caching here so an admin edit lands on the next request rather than the next restart. `GET /characters/defaults` filters `is_published = true` (an admin can draft an entry invisible to vgai2 until it's ready) and is **unauthenticated**, same "public browsing, gated actions" rule; `POST /characters/defaults/{slug}/import` is gated, filters `is_published = true` too (a hidden draft must not be importable by guessing its slug), and takes *only* a slug, so a tampered payload can't smuggle in different content. Two things differ from the style-template version, both deliberate. **(1) The import makes a real *Cloudinary* copy of the sheet** (`copy_image_from_url()` into `<user_id>/characters/`), not just a copied URL string: `character_sheet_url` is the character's actual content, so leaving every importer pointed at the catalog's own asset would mean deleting a catalog entry blanks the image for all of them — the exact bug `project_characters` had and was fixed for (see the character-import note in this file). The style-template catalog's own import was then brought onto this same rule for its `demo_image_url` (see that bullet), so both catalogs now copy rather than reference. `_IMPORTABLE_FIELDS` is therefore only `("name", "description")`, with the URL handled separately; `best_for` is catalog-browsing guidance rather than part of the character, so it isn't copied either. **(2) An import is never auto-marked `is_default`**, unlike a user's first imported style template. `characters` has no one-default-per-user constraint and `POST /projects/create` snapshots *every* default character into each new project, so auto-defaulting an import would silently push a stock character into every project the user goes on to create; they opt in with the card's own "Set default" toggle instead. Registered before `characters_crud` in `router.py`, same literal-path-first discipline as the styletemplates routers.
- **`style_templates.best_for` / `.demo_image_url`** are both nullable and written only from the form's Advanced Settings. `best_for` ("History, biography, philosophy") is user-facing pick-between-templates help — it is **not** sent to any LLM; the scene-splitting directive lives in `description`. `demo_image_url` is a sample frame previewed on the card so a 20-template library stays scannable. Neither is snapshotted onto `projects` (neither is read at generation time), so the 8-field style-template snapshot rule is unchanged. The image can reach the field three ways — paste a URL, upload on pick via `POST /styletemplates/upload_demo_image`, or a "Generate" button next to it that calls `POST /styletemplates/generate_demo_image` — all three land in the same `demoImageUrl` form field, so create/update never need to know which one was used. Both upload and generate endpoints live in `crud.py` (not `generatetemplate.py`, which is reserved for the separate "Generate Style Template" AI-draft flow that writes a whole new template's fields) since generating a demo image fills one field on the plain create/update form the same way uploading one does, rather than drafting a template. The generate path is a flat `GENERATE_DEMO_IMAGE_CREDIT_COST = 4` (misc-spend, same reserve-before-call/refund-on-failure shape as the AI-generation pattern above) for one `gpt-image-2` call at `quality="low"` (`DEMO_IMAGE_SIZES`, `1792x1008` for 16:9 / `1008x1792` for 9:16, both multiples of 16 per the same gpt-image-2 constraint noted on `characters/generatecharacter.py`'s `SHEET_IMAGE_SIZE`) — **no separate LLM call rewrites the prompt first**: `_build_demo_image_prompt()` builds it directly as a plain string template ("Generate a demo image in this art style: {image_prompt}. Most used categories: {best_for}.") straight from the form's own `image_prompt`/`best_for` fields, since those already describe the style and its intended niche well enough to hand to the image model as-is, plus a fixed trailing safety clause (no graphic violence/gore/nudity/hate symbols, express dark mood through color/lighting instead) since a style whose own wording leans dark (horror, noir, true-crime, war) has a real chance of gpt-image-2 flagging its own *output* on moderation grounds even when the prompt itself is fine. `_generate_demo_image_bytes()` wraps the actual call with one retry: if the first attempt raises OpenAI's `moderation_blocked` 400 (detected via `_moderation_blocked()`'s string match on the error body, not an SDK exception-class check, since it has to survive whichever concrete exception type raises it), it retries once with an even more conservative prompt steering toward a calm, non-graphic, non-dramatic subject; only if that retry is *also* blocked does it give up, surfacing a clear 422 telling the user to soften the Image Prompt/Best For wording rather than leaking the raw OpenAI error string. Unlike the accept/reject-preview AI-generation pattern, this endpoint uploads straight to Cloudinary and returns a real URL (the same shape `upload_demo_image` already returns) rather than a base64 draft — there's no separate accept step since the result only fills the form field a manual upload would, and the user still reviews/can replace it before saving the template itself; the upload call is inside the same try/except as the OpenAI call so a Cloudinary failure after a successful generation still refunds. `GenerateStyleTemplatePopUp.tsx`'s "Generate demo image" toggle (see the AI-generation pattern bullet above) reuses this exact same `_generate_demo_image_bytes()` helper via `generatetemplate.py`'s `_generate_and_upload_demo_image()`, so the moderation-retry behavior is identical on both paths rather than duplicated. Cleanup on replace/delete is guarded by `_owns_demo_image()`: a template imported from the catalog points at a *shared* asset every other importer also references, so `delete_media()` on it would blank the preview for everyone — same trap as `project_characters.snapshot_character_sheet_url`. Only assets under `<root>/<user_id>/style_templates/` are ever deleted.
- **`/generate_script` AI pattern** (`scriptgenerationtemplate/viralscripttopicresearch.py` + `crud.py`, both under the shared `/scripttemplates` prefix — routers registered in that order in `router.py` specifically so `viralscripttopicresearch`'s literal paths like `/generatedscripts` aren't shadowed by `crud.py`'s dynamic `/{scripttemplate_id}`): unlike the AI-generation pattern above, this flow is **fully DB-backed as it happens** — there's no accept/reject-into-`create` step, every successful call writes straight to `researched_topics`/`generated_scripts`. `/generatetopics` (Perplexity `sonar-pro`, flat `TOPIC_RESEARCH_CREDIT_COST` of 5) either creates a fresh `script_templates` row (`is_saved=false`, when the request has no `script_template_id`) or updates an existing one's fields, then **upserts** 10 `researched_topics` rows keyed on `(script_template_id, topic_number)` — so re-researching the same session updates those same 10 rows in place instead of accumulating. `/generatescript` and `/improvise` (both Claude `sonnet-5`, cost = `ceil(script_word_length's upper bound / WORDS_PER_CREDIT)`, `WORDS_PER_CREDIT = 30`, e.g. an "800-900" band costs 30 credits) only take `{script_template_id, topic}` / `{generated_script_id, feedback}` — every other field (category, descriptions, country, word length) is read back from the DB row, never re-trusted from the client, and `/generatescript` inserts a new `generated_scripts` row while `/improvise` updates one in place via `_get_owned_generated_script()`. `PUT`/`DELETE /generatedscripts/{id}` let a user manually edit or remove a generated script directly (no AI call, no credit cost). `GET /generatedscripts` returns *all* of a user's generated scripts globally (not scoped to one session) so they survive across page reloads; `GET /{id}` and `GET /{id}/topics` (both in `crud.py`) let the frontend restore a session's form state + topics after a reload. Characters are stored on `generated_scripts.character_involved` as delimited text — `|||` between characters, `::` between each character's fields (`_serialize_characters()`/`_parse_characters()`) — deliberately not `#`/`,`, which can plausibly appear inside AI-generated names/descriptions. Same balance-check-then-deduct shape as the AI-generation pattern above (`_check_and_get_balance()`/`_deduct_credits()` helpers). Both LLM calls go through `app/openrouter_client.py`'s `get_openrouter_chat_model()` (`ChatOpenAI` pointed at OpenRouter's `base_url`, same class as the OpenAI flows) — Claude calls use `.with_structured_output()`; the Perplexity call does not (uncertain tool-calling support), so `/generatetopics` instead prompts for raw JSON and parses it defensively (`_parse_topics_json()`, strips code fences / extracts the first `[...]` block) rather than trusting structured output. `script_templates.is_saved` distinguishes an explicit "Save as Template" (`POST /create`, `is_saved=true`, shown in "My Templates") from the auto-created row behind a research/generate session (`is_saved=false`, invisible to `GET /` which filters on `is_saved=true`) — `POST /create` reuses the session's row (via an optional `script_template_id` in the payload) instead of inserting a duplicate when one already exists.
- **Payments**: `app/routes/payments/crud.py` implements Razorpay credit top-ups — `POST /payments/create-order` creates a Razorpay order + a `pending` `credit_topups` row priced off a fixed `PAISE_PER_CREDIT` (INR-only; see its module comment for why), `POST /payments/verify` verifies the Razorpay Checkout signature and applies the credits. **The charge is computed per *credit*, not per dollar** — `amount_paise = credits * PAISE_PER_CREDIT`, where `PAISE_PER_CREDIT = USD_TO_INR_RATE = 100` makes 1 credit exactly ₹1. `AddCreditsPopUp.tsx`'s "You'll be charged" preview mirrors that same formula off the same-named constant rather than converting the user's USD input at a separate rate: it previously carried its own `INR_PER_USD = 97` and so quoted $5 as ₹485 against a real ₹500 charge. Two constants multiplying two different quantities is what let them drift silently — keep the frontend `PAISE_PER_CREDIT` numerically in sync with this one, nothing enforces it. Note the wider framing problem this exposed, currently unresolved and deliberately so: the UI collects USD but charges INR at a rate well above market, which reads as a bad conversion rather than as regional pricing. The likely direction is standardizing on USD (most users aren't in India, and every provider bill is already USD), which needs Razorpay international payments approved on the account first — plus a real minimum charge, since `MIN_CREDITS = 10` becomes an unprocessable $0.10 — and would make `credit_topups.currency` genuinely mixed, breaking `GET /payments/history`'s single `total_amount_paid` sum. `app/routes/payments/webhook.py` is a written-but-unregistered backup path for the case where a payment succeeds but the user closes the tab before `/verify` fires — see its docstring for why it's inactive (needs a real deployed domain) and how to turn it on. `GET /payments/history` is the read side, feeding the `/profile` page's Payment History tab — it returns *all* `credit_topups` rows including `pending`/`failed` ones (a `pending` row is written by `/create-order` before Checkout opens, so dismissing the Razorpay modal leaves one behind permanently; showing them means an abandoned attempt reads as abandoned rather than as a payment gone missing) but totals **only** `success` rows, since nothing was charged for the rest.
- **`/profile` usage history**: `app/routes/profile/usagehistory.py` (`GET /profile/usage-history`) serves the other tab of that page. The two halves are deliberately split by the table they read rather than by the page they feed — `credit_topups` belongs to the payments router above, while this one reads `project_expence_tracker` (one running-total row per project) plus `users.miscellaneous_credit_spent`. Because that tracker table has no FK back to `projects` (exactly what keeps a deleted project's spend queryable), "does this row still point at a live project?" can't come from a join: the endpoint does one extra `projects` lookup keyed on the collected `project_id`s and returns `project_exists` + a real `project_created_at` for the survivors, falling back to `first_spend_at` (the tracker row's own `created_at`) for the rest. `total_credit_spent` is lifetime spend across *everything* — the four project-scoped columns plus miscellaneous — so the five sub-totals beside it add up to exactly that figure.
- **`/project_folder` pattern** (`app/routes/project/`, 7 registered route files — `projectcrud`, `paidscripttoscenesplitter`, `freescripttoscenesplitter`, `generatedscenecard`, `imagegeneration`, `imageregeneration`, `animationgeneration` — plus 1 unregistered stub (`voiceovertts.py`) and `scenesplitcommon.py`, a shared non-router module): `projectcrud.py` owns the `projects`/`project_characters` resources (`GET/POST/PUT/DELETE /projects/...`, `.../characters/...`, `.../styletemplate/import`, `.../voiceoversettings`) and exports `_get_owned_project()` (same ownership-check shape as `characters/crud.py`), which every other file in this package imports. `projectcrud.py` also exposes `PUT /projects/{project_id}/characters/{project_character_id}` — edits one `project_characters` row's `snapshot_name`/`snapshot_description` and, optionally, uploads a replacement sheet image to a new `<user_id>/<project_id>/project_characters/` Cloudinary folder rather than overwriting the shared `characters/` asset the snapshot originally pointed at (`_owns_project_character_image()` gates `delete_media()` on the old value, same "only ever delete what this scope actually uploaded" shape as `_owns_demo_image()` in `styletemplates/crud.py` — see the Cloudinary bullet below). `ProjectUpdate` (see Schemas bullet below) also gained the 9 `snapshot_styletemplate_*` fields so `PUT /projects/update/{project_id}` can edit a project's own style-template snapshot directly. Both endpoints back `ChooseCharacterPopUp.tsx`/`ChooseStyleTemplatePopUp.tsx`'s "View/Edit for this project" flow — see Frontend architecture's "Editing an imported snapshot" bullet — and neither ever writes to `characters`/`style_templates` or any other project's snapshot. Credit handling comes from `app/credits.py` instead: `reserve_project_credits()`/`refund_project_credits()` differ from the misc-spend pair only in where the spend is booked — a *running per-project* `project_expence_tracker` row (one row per project, upserted-and-incremented) rather than `users.miscellaneous_credit_spent`, per README §2's per-project-vs-miscellaneous split. `paidscripttoscenesplitter.py` (`POST /projects/scenes/generate_automatic`) is the "Generate Scenes (Automatic)" call: one structured-output LLM call (`gpt-4o` for `"base"`, `gemini-3-pro-preview` via `app/gemini_client.py`'s `get_gemini_chat_model()` for `"pro"`) given the style-template snapshot + project characters (name/description only) + full script, returning `scenes[]` + `metadata` + `compact_image_prompt`/`compact_animation_prompt`. `freescripttoscenesplitter.py` is its free counterpart, and unlike the automatic flow it's **two endpoints, split so the credit charge lands before the prompt is handed over**: `POST /projects/scenes/generate_manual_charge` reserves the cost the instant the trigger button is clicked (before `GenerateScenesManualPopUp.tsx` opens), and `POST /projects/scenes/generate_manual` then parses/persists the JSON the user pasted back from running our prompt through gemini.com themselves, charging nothing (`credits_spent: 0`, `credits_remaining` re-read via `get_balance()` purely so the frontend can resync). The split exists because the popup's entire value is the prompt it reveals — charging on paste-back means a user can copy that prompt, run the split on gemini.com, and generate images/animations outside vgAI having paid nothing, since nothing forces them to ever paste a result back. `GenerateScenesManualPopUp.tsx` builds that prompt client-side, mirroring the automatic flow's system message/style-brief/character-list formatting closely enough that Gemini's output matches the same schema. Both endpoints share `_validate_manual_preconditions()` (script present + style template imported, plus the cost calc) so a project that can't legally split also can't be charged, and neither can accept a paste-back. Scene numbers are always re-sequenced 1..N in Python regardless of what the draft contained. `scenesplitcommon.py` also holds `WORDS_PER_CREDIT_AUTO = 10` / `WORDS_PER_CREDIT_MANUAL = 100` (manual is priced 10x cheaper per word since no provider is billed, though credits are still reserved via the same `reserve_project_credits()` call — manual scene generation is not free of cost, just free of LLM spend) and both scene-*persisting* endpoints return the same `GenerateScenesResponse` schema (`app/schemas/scene.py` — renamed from `GenerateScenesAutomaticResponse` now that a second endpoint returns it). `imagegeneration.py` (`POST /projects/image/generate_and_save`, `/generate_thumbnail_and_save`) and `animationgeneration.py` (`POST /projects/animation/generate_and_save`) generate a scene's image/animation or the project's thumbnail — image generation uses `openai_client.images.edit()` with a *list* of reference images when the scene/project has involved characters (vs `images.generate()` when it doesn't). `imagegeneration.py` also has `POST /projects/image/generate_manual`, the manual/no-provider counterpart of `generate_and_save` — it calls no image API at all (the user pastes batched prompts + character sheets into meta.ai themselves via `ManualImageGenerationPromptCopyPopUp.tsx` on the frontend) and just charges `ceil(scene_count / SCENES_PER_CREDIT_MANUAL)` credits (`SCENES_PER_CREDIT_MANUAL = 5`), reading scene count from the DB rather than trusting it from the client, same reasoning as `freescripttoscenesplitter.py`'s manual scene split. `generatedscenecard.py` additionally exposes `POST /projects/scenes/{scene_id}/upload_image` / `upload_animation` and `DELETE /projects/scenes/{scene_id}/image` / `animation` — free, no-AI-call convenience endpoints (same shape as the rest of that file's plain CRUD) letting a user attach an image/animation they produced outside vgAI, or remove one outright. - **`imageregeneration.py`** (`app/routes/project/imageregeneration.py`, registered right after `imagegeneration.py` since it imports straight from it): two endpoints for AI-assisted prompt iteration on an existing scene, both a flat `REWRITE_CREDIT_COST = 1` on top of whichever other cost applies. `POST /projects/image/sync_animation_prompt` rewrites *only* `scene_animation_prompt` (via `ChatOpenAI` `gpt-4o-mini`, structured output) to match a `scene_image_prompt` the user just hand-edited — triggered from the frontend only after an explicit confirm, since it's not free. `POST /projects/image/regenerate_and_save` is what "Regenerate" now calls once a scene already has an image: rather than resubmitting the exact prompt that produced a disliked result, it first has the LLM rewrite *both* `scene_image_prompt` and `scene_animation_prompt` (told the previous result was disliked, told to vary composition/action while preserving style exactly — art style, technique, camera/motion constraints, aspect ratio, sourced from `scenesplitcommon.py`'s `format_style_brief()`), persists them, and only then generates the new image from the rewritten prompt, reusing `imagegeneration.py`'s `_generate_image_bytes()`/`_quality_and_cost()`/`_image_size_for()` plus the same generation-token/cancellation/previous-asset-cleanup shape as `generate_scene_image`. The two costs (`llm` for the rewrite, `image` for the generation) are reserved as **separate** `reserve_project_credits()` calls so `/profile`'s per-category usage breakdown stays accurate — if the image-cost reservation itself fails (insufficient balance), the already-spent rewrite credit is refunded too (the promised regenerate never happened), but if the image *generation call* fails after that, only the image credit is refunded — the rewritten prompts are real, saved, reusable work regardless of whether the image itself succeeded.
- **Cancelling a generation charges for it but discards the result.** Credits are already spent by the time Cancel is clicked (see the credits bullet above), so cancelling can't get them back — what it does guarantee is that the abandoned asset never appears. Each generation stamps a `*_generation_token` uuid on its row (`_start_generation()` in `generatedscenecard.py`) and every write-back goes through `_finish_generation()`, which is a conditional update guarded on that token; `POST /projects/scenes/cancel_generation` clears it, as does starting a new generation. So a slow request the user cancelled — then edited the prompt and re-ran — finds its token gone, deletes the Cloudinary asset it just uploaded, and returns 499 instead of overwriting the newer result. Without this, image generation had a real overwrite bug: its Cancel is frontend-only (`AbortController`; a single blocking OpenAI call can't be abandoned server-side), so the orphaned request always ran to completion and saved. Animation additionally stops early — `openrouter_video.generate_video_from_image_url()`'s job-polling loop checks `await request.is_disconnected()` each iteration — but OpenRouter has already billed the submitted job, which is exactly why cancelling is not a refund. Animation passes the scene's already-hosted Cloudinary image URL straight through as OpenRouter's `frame_images` input (no download/re-upload needed, unlike the multi-character-reference image path above). `generatedscenecard.py` is plain scene CRUD (`GET/POST/PUT/DELETE /projects/scenes/...`, no AI call, no credit cost — reordering via `scene_number` is out of scope), plus the generation-token helpers (`_start_generation()`/`_finish_generation()`) and `POST /projects/scenes/cancel_generation` that the two generation modules build on. `voiceovertts.py` (voiceover generation) is the one remaining empty, unregistered stub in this package — deliberately deferred, see the Current-state note above. Assets upload to `<CLOUDINARY_FOLDER_NAME>/<user_id>/<resource>/...`; see `README.md` §9 for the full folder layout — `characters/`, `<project_id>/{scene_images,scene_animation,thumbnail_image}/`, and `<project_id>/project_characters/` are all wired up now. `_owns_project_character_image()` still gates every `delete_media()` on a `project_characters` row (in `update_project_character()`, `remove_project_character()`, and implicitly via `delete_project_media()`'s prefix scoping) — every row in the DB is confirmed to already own its image copy as of this fix (a one-time backfill script migrated the single pre-fix row that existed, then was deleted once its job was done), so the guard isn't load-bearing today, but it's cheap insurance left in place in case a restored backup or another environment ever reintroduces an old-style row. `voiceovers/` is still not wired up (voiceover generation is still a stub). `delete_media()` is best-effort (swallows errors) since a Cloudinary asset already gone shouldn't block a DB delete. **Nothing is left behind**: `characters/crud.py` deletes a character's sheet on both delete and on a sheet-replacing update; `generatedscenecard.py`'s `delete_scene` deletes its image + animation; every regenerate path (`imagegeneration.py`'s scene-image and thumbnail generation, `animationgeneration.py`'s scene-animation generation) captures the row's *previous* asset URL before generating and deletes it once the new one is successfully saved (never on a cancelled/failed attempt, since then the old asset is still what the row points at) — none of this applies to the character-generate preview flow, since `generatecharacter.py` returns the drafted image as a base64 data URI and never touches Cloudinary until the user accepts and it goes through `characters/crud.py`'s normal upload, so a rejected draft has nothing to clean up. `scenesplitcommon.py`'s `persist_scene_split()` (both "Generate Scenes" flows — see the `/project_folder` bullet above) is the same discipline one level up: re-splitting deletes every existing scene's image + animation *and* the project's thumbnail (clearing `thumbnail_image_url`/`thumbnail_generation_token` on the row too), since a re-split — whether from an edited script or just a different roll of the same script — makes every previously-generated asset stale with no reliable way to tell which ones "still match." `delete_project_media(user_id, project_id)` is the one exception to per-asset cleanup: rather than replaying tracked scene/thumbnail URLs, `projectcrud.py`'s `delete_project` calls it to delete every image/video resource by folder-prefix under `<root>/<user_id>/<project_id>/` (catching anything not currently referenced by a row, e.g. a stray upload) and then removes the now-empty subfolders and the project folder itself — scoped so it can never reach `<root>/<user_id>/characters/`. That prefix scoping is also why this now correctly cleans up a project's `project_characters` image copies too (they live under the same `<project_id>/` prefix as of the import fix above); a pre-fix, not-yet-backfilled row pointing outside that prefix at the shared `characters/` asset is simply not touched by it, which is the safe outcome either way.
- **Access control** (`app/access_control.py`, called from `app/auth.py::get_current_user` — the single dependency every protected route, including `POST /users/sync` right after login, goes through): enforces the `access_control_list`/`access_system_settings` tables that the separate **vgai2admin** repo writes (same shared DB, see its own `CLAUDE.md`/`README.md` §4 for the admin-side design and the empty-allowed-list lockout guard). Checked on *every* request, not just login, since a Supabase JWT self-refreshes and stays valid after issuance — a restriction has to take effect mid-session, not just block new logins. Mode + the one relevant list (restricted under `allowed_all`, allowed under `allowed_only`) are cached in-process for 30s (`_CACHE_TTL_SECONDS`) as `dict[email, note]`, not just a set of emails — rather than queried per request; the check fails open on a lookup error so a DB hiccup here can't lock out every signed-in user. A blocked email gets a 403 with `detail = {"code": "ACCESS_REVOKED", "message": ..., "mode": ..., "reason": ...}`, not a 401 — 401 means "refresh and retry," which is wrong here. `reason` is the admin's note on the matching restricted-list entry (`allowed_all` mode only — an `allowed_only` block is an absence from the allowed list, which has no per-user note to surface); `mode` and `reason` exist specifically so the frontend can explain *why*, not just *that* (see below). `get_public_mode()` exposes the mode alone (never the lists) for `GET /users/access_status` (`app/routes/users.py`, unauthenticated) — the Navbar's ambient invite-only indicator needs this before anyone has signed in. Verified against real production data (restricted-list insert → 403 → remove → allowed again, case-insensitive on the email match; the `reason` round-trip verified separately with a real note).
- **Supabase**: `app/supabase.py` exports a singleton `supabase` client built with the *secret* (service-role) key — it bypasses Row Level Security, so any per-user access scoping has to be enforced in route code, not assumed from RLS. The `_get_owned_<resource>` helper pattern in `characters/crud.py`/`styletemplates/crud.py`/`project/projectcrud.py` (fetch by id, 404 if missing or `user_id` mismatch) is how that scoping is done — follow it for new resources. `project/generatedscenecard.py`'s `_get_owned_scene()` is the same idea one level down (scenes have no `user_id` column, so it checks ownership via the parent project).
- **Schemas**: request/response models live in `app/schemas/*.py` as plain Pydantic models per resource. `character.py`, `styletemplate.py`, and `payment.py` are aligned to their DBML tables (plus the two `Generate*Request`/`Generate*Response` pairs for the AI-generation endpoints, which aren't DB-backed). `scripttemplate.py` is fully DB-backed (unlike the other two `Generate*` pairs) — `ScriptTemplate`/`Create`/`Update` map to `script_templates`, and `TopicResearchResponse`/`ScriptGenerateResponse`/`ScriptImproviseResponse`/`GeneratedScriptRecord` all round-trip through `researched_topics`/`generated_scripts`, not just describe an ephemeral draft. `project.py`/`scene.py` map to `projects`/`scenes` the same fully-DB-backed way; `ProjectUpdate` is the one schema in the codebase using `model_dump(exclude_unset=True)` partial-update semantics rather than full-replace, since rename/script-autosave/model-tier-pick/thumbnail-prompt-autosave are separate UI surfaces each touching different fields — `thumbnail_prompt` in particular is read straight off the `projects` row by `imagegeneration.py`'s thumbnail endpoint at generation time, so editing it via `VideoMetaDataCard.tsx`'s autosave-on-blur field (see Frontend architecture below) is enough to change what the next "Regenerate Thumbnail" click actually generates, with no other backend change needed. `ProjectUpdate` also carries the 9 `snapshot_styletemplate_*` fields (added for `ChooseStyleTemplatePopUp.tsx`'s project-scoped style-template edit — see Frontend architecture) — a one-way, project-local write that never touches `style_templates` or any other project.

## Frontend architecture

- **App Router + client-heavy pages**: routes live under `frontendweb/src/app/`. Existing pages so far use `"use client"` liberally (see `page.tsx`); shared chrome lives in `frontendweb/src/components/`.
- **CLS discipline — loading states must reserve their real space**: `app/(app)/layout.tsx` is now a plain server component with no auth gate — it used to block `<MainLayout>` (Sidebar/Navbar/Footer, the whole chrome) behind a bare full-screen spinner while `useAuth()`'s initial `getSession()` resolved, then swapped in an entirely different tree once it did, on every full page load. That was removable outright because Sidebar/Navbar already render correct logged-out states for a null `user` (`requireAuth()`-gated actions, not gated views — see the bullet below), so there was nothing left to block on. Below that shell, `characters/page.tsx`, `style_templates/page.tsx`, and `liked_projects/page.tsx` all replace a bare centered spinner with `components/CardGridSkeleton.tsx` (`variant="media"` for the two image-topped card shapes, `variant="panel"` for Style Templates' icon+title header shape) — pass the *exact* grid className the loaded state renders or the swap still reflows. All three now pass `count={PAGE_SIZE}` (10, matching their own pagination — see the bullet below): since a page can hold at most 10 items, that's a real upper bound rather than a guess, so the skeleton only overshoots on a page with fewer than 10 real items left to show, not by an arbitrary margin. (The component's own default of 4 only matters for a caller with no pagination behind it, where item count truly can't be bounded in advance.) `/project_folder/{id}`'s loading state (`project_folder/[project_id]/page.tsx`) reserves space for its fixed-height header/script/menu/action-row section (identical on every project) plus two generic scene-card-shaped placeholders as a "more is coming" signal — scene count varies per project, so unlike the card grids this one can't be pixel-exact even in principle. `/login`'s spinner-to-card swap was deliberately left alone — it's the page's only content, so nothing else shifts. `style_templates/page.tsx`'s "Starter Templates" header button is the same discipline applied to a single button rather than a whole grid: it used to be omitted outright (`{defaults.length > 0 && <button>...}`) until the public catalog fetch resolved, so it was reliably absent on first paint and popped into the header row a moment later on every load — the exact "swaps in an entirely different tree" pattern this bullet already forbids, just at button scale instead of page scale. Fixed with a `defaultsLoading` state (starts `true`, cleared in the catalog fetch's `.finally()` regardless of success/failure) gating a same-sized skeleton (identical padding/ring/icon-and-text-width classes, pulsing placeholder blocks) in the button's place until the fetch settles, at which point it swaps to the real button with no shift. The one shift this doesn't eliminate — skeleton collapsing to nothing if the catalog turns out empty or the fetch fails — is accepted rather than avoided, same reasoning as `CardGridSkeleton`'s own default-count caveat above: it only fires on the uncommon path, not the one every page load hits.
- **Layout shell**: `layout.tsx` wraps every page in `ThemeProvider` → `SplashScreen` + `MainLayout`. `MainLayout` renders `Sidebar` + `Navbar` + page content + `Footer`, and owns the mobile sidebar open/close state (sidebar is an off-canvas drawer below `md:`).
- **Theme**: dark mode is a `dark` class on `<html>`, decided pre-hydration by an inline script in `layout.tsx` (reads `localStorage.theme`, falls back to `prefers-color-scheme`) to avoid a flash of the wrong theme. `ThemeProvider` (`components/ThemeProvider.tsx`) mirrors that into React state after mount and exposes `useTheme()`/`toggleTheme()` for interactive toggling; keep both in sync if you touch theme logic.
- **Sidebar/Navbar match the README spec**: `Sidebar.tsx` implements the `README.md` §4 structure — a Library section (Characters, Style Templates, Generate Scripts, Liked Projects) that's always visible/clickable even when logged out, and a Project Folders section that shows a login-gated message instead of the project list when logged out. When logged in, that section is a live list from `ProjectsContext` (create/rename/delete/like, same `ConformationMessagePopUp` delete-confirmation pattern as the library pages) rather than a placeholder. Each row shows a yellow `Folder` icon, the name, an always-visible heart (like/unlike) and trash (delete) button — no hover-to-reveal, unlike the pencil-based edit affordance the library cards use — and a native `title` tooltip with the project's created date on hover. Renaming is double-click-on-the-name rather than a pencil button: a single click is debounced `NAVIGATE_DELAY_MS` (220ms) before it navigates to the project, and a second click landing within that window cancels the navigation and starts inline rename instead (the classic single-vs-double-click disambiguation, since a `dblclick` is preceded by two real `click` events). `Navbar.tsx` has Home/About/Contact (no login required to view), a credit-balance pill (links to `/profile`) when logged in, and either an account-avatar menu or a "Login" button depending on auth state.
- **Shared project list** (`context/ProjectsContext.tsx`, mounted in root `layout.tsx` next to `CreditBalanceProvider`): holds the `{id, name, is_liked, thumbnail_image_url, created_at}[]` list `Sidebar.tsx`, `generate_script/page.tsx`'s Import flow, and `/liked_projects` all need, with `createProject()`/`renameProject()`/`removeProject()`/`toggleLike()` methods that update local state immediately (no extra round-trip) so a rename/delete/like from the sidebar, `/liked_projects`, or the project page itself stays in sync everywhere instantly — same reasoning as `CreditBalanceContext`. `toggleLike()` is optimistic (flips `is_liked` in state before the `PUT /projects/update/{id}` call resolves, reverting on failure) specifically so liking in the sidebar and seeing the change on `/liked_projects` (or unliking there and seeing it vanish) has no lag — both read `is_liked` off this one shared list rather than each fetching their own copy, which is what `README.md` §5 means by "single source of truth." The `/project_folder/{project_id}` page itself does its *own* separate `GET /projects/{id}` fetch for full project detail (script, snapshots, settings) — this context only holds the list-view subset.
- **`/liked_projects`**: filters `ProjectsContext`'s list down to `is_liked` projects and renders them via `components/liked_projects/LikedProjectsCard.tsx` (Cloudinary thumbnail if the project has generated one, otherwise a yellow-folder placeholder; a filled-red heart button unlikes via the same `toggleLike()`). Not a separate fetch or its own local like-state — unliking here and liking in the sidebar hit the same context method, which is what keeps the two in sync.
- **Pagination**: `hooks/usePagination.ts` (`usePagination(items, pageSize)`) + `components/Pagination.tsx` are the shared pair behind every paginated list in the app — `characters/page.tsx`, `style_templates/page.tsx`, `liked_projects/page.tsx`, `generate_script/page.tsx`'s generated-scripts list, and both tabs of `PaymentAndUsageHistoryTabCard.tsx`, all at `PAGE_SIZE = 10`. All client-side: every one of these lists already comes from a single GET with no page/limit params, so slicing an already-fetched array avoids a second round trip per page turn (and for the profile history tabs specifically, the totals have to sum across *every* row regardless of which page is showing, which a server-paginated endpoint would need a separate aggregate query for). The hook clamps `page` against the *current* `pageCount` on every render rather than storing it pre-clamped, so a list shrinking out from under an open page (e.g. a delete) snaps back on its own with no explicit reset — but growing at the front does need one: every "create"/"generate" handler that prepends a new item (`handleGenerated`/the manual-create branch in characters and style_templates, script generation in `generate_script`) also calls `setPage(1)`, since otherwise a successful create could silently land on a page the user isn't looking at. `generate_script`'s "Script #N" numbering (counts up from the earliest generated, per README) is computed from each item's position in the *full* array before pagination slices it, specifically so the number a card shows doesn't depend on which page it's currently on. `style_templates/page.tsx`'s own grid additionally filters by aspect ratio (All / 16:9 · Long Video / 9:16 · Reels, a pill-button toolbar above the grid) *before* handing the result to `usePagination` — `filteredTemplates`, not `templates`, is the hook's input — so `pageCount`/`totalItems` reflect the filtered set, not the full library; switching the filter also calls `setPage(1)` for the same "don't silently land on an out-of-range page" reason as the create/generate handlers above (the hook's own auto-clamp would recover from this on the next render regardless, but jumping to page 1 immediately reads better than a page flash). `DefaultStyleTemplateCardPopUp.tsx`'s catalog grid has the identical filter (same three options, independent local state) but isn't paginated, so it just filters `defaults` directly before the `.map()`.
- **`AuthContext`'s `user` is memoized by id, not re-derived from `session` on every render** (`context/AuthContext.tsx`): Supabase hands out a brand-new `session` object — and so a new `session.user` reference — on every token refresh and window focus, not just on a real sign-in/out. Effects across the app used to key their dependency array on this `user` object (`ProjectsContext`, `CreditBalanceContext` — both mounted app-wide off root `layout.tsx` — plus the characters/style_templates/generate_script pages) expecting it to only change when who's signed in actually changes; without the memo, all of them re-fired and re-fetched from the backend on a plain token refresh, and on `/profile` specifically it was worse — the effect flipped `loading`, which unmounted and remounted `PaymentAndUsageHistoryTabCard`, discarding its selected tab and fetch cache on a timer unrelated to the user changing. Fixed once at the source (`useMemo(() => session?.user ?? null, [session?.user?.id])`) rather than chasing every call site — any new effect keyed on `user` gets this for free.
- **Accessible names on icon-only controls**: every icon-only `<button>` in the app (popup close `X` buttons, the mobile hamburger/close pair on Navbar/Sidebar, the rename/create inputs in `Sidebar.tsx` and `project_folder/[project_id]/page.tsx`'s header) has an explicit `aria-label` — a Lighthouse Accessibility check ("Buttons/inputs do not have an accessible name") that a large icon-heavy UI like this one hits often. Popup close buttons uniformly use `aria-label="Close"`; keep that convention for any new popup rather than inventing per-popup wording, since it's the expected name for a modal dismiss control. Most edit/delete/toggle buttons across the card components (`CharacterCard`, `StyleTemplateCard`, etc.) already did this correctly before this pass — follow their pattern (`aria-label={`Edit ${item.name}`}`-style, specific to the item) for anything that isn't a generic dismiss control.
- **`ACCESS_REVOKED` handling** (`lib/api.ts`'s `authFetch`, `AuthContext.tsx`'s `syncUserWithBackend`, `components/AccessRevokedModal.tsx`, `components/Navbar.tsx`): the frontend half of the access-control feature above. Both places that can hit the backend's 403 `{code: "ACCESS_REVOKED", mode, reason}` — the general `authFetch` wrapper used app-wide, and the login-time `POST /users/sync` call, which uses a raw `fetch` rather than `authFetch` since it fires before there's necessarily a caller expecting a thrown error — dispatch a `window` `"vgai:access-revoked"` event carrying that `{mode, reason}` in `detail`, rather than surfacing it as an ordinary fetch error, since `authFetch` is called from dozens of unrelated components with no `AuthContext` access. `AuthContext` listens for that event, reads the blocked email off the still-live session via a ref (`sessionRef`, kept current in its own effect rather than assigned during render — React disallows mutating a ref mid-render, and the handler is registered once with `[]` deps so a plain closure over `session` state would be permanently stale), calls `supabase.auth.signOut()`, and flips `accessRevoked` plus `accessRevokedMode`/`accessRevokedReason`/`accessRevokedEmail`. `AccessRevokedModal` (mounted once in root `layout.tsx`, next to `LoginModal`) isn't dismissible by clicking outside — unlike `LoginModal`, this fires mid-session after the user is already signed out, so there's no "cancel and keep going" state to return to — and shows one of two messages depending on `accessRevokedMode`: `allowed_only` ("this app is invite-only, and `<email>` isn't on the list" — no admin reason exists for an absence) vs `allowed_all` ("access revoked" + the admin's `reason` when there is one). Separately, `AuthContext` also fetches `GET /users/access_status` once on mount (independent of sign-in state — it's unauthenticated) into `accessMode`; `Navbar.tsx`'s `AccessModeBadge` renders only while `accessMode === "allowed_only"` (the default mode needs no explanation), showing a green "you're allowed" pill to a signed-in user (reaching this render signed in already proves the allowed-list check passed — no separate "am I allowed" call needed) or a neutral "invite-only mode" pill to a signed-out visitor who hasn't attempted sign-in yet.
- **Public browsing, gated actions**: nothing forces a login redirect on page view — `(app)/layout.tsx` renders `MainLayout` regardless of auth state. Write actions (create/edit/delete/generate) call `requireAuth()` from `AuthContext` (`context/AuthContext.tsx`) first; if signed out, it opens the global `LoginModal` (rendered once from root `layout.tsx`) and returns `false` so the caller bails out. Follow this pattern for any new write action rather than redirecting to `/login`.
- **`AuthContext.user` is a three-state value, not a boolean — treat "unknown" and "confirmed logged out" as different states.** `AuthContext.loading` starts `true` and only flips `false` once Supabase's initial `getSession()` (or its first `onAuthStateChange` fire) resolves; until then, `user` is `null` simply because the real answer isn't known yet, not because anyone is actually logged out. Any code that branches on `!user` to show a "please log in" view — without first checking `authLoading` — will flash that logged-out UI on every hard refresh of an *already-authenticated* session, for however long `getSession()` takes to resolve (fast on a warm localStorage read locally, but not instant, and not guaranteed fast in production). This bit `Navbar.tsx` (flashed the "Login" button before the credit pill), `Sidebar.tsx` (flashed "Login first to see or create your projects" before the real project list), `ProjectsContext.tsx`/`CreditBalanceContext.tsx` (both actively cleared their state — `setProjects([])`/`setBalanceState(null)` — the instant `user` read `null`, which is what fed the wrong data into Navbar/Sidebar/`/liked_projects` in the first place), and the `characters`/`style_templates`/`generate_script`/`liked_projects` pages' own "Login to view your X" branches. The fix, applied consistently everywhere above: read `loading: authLoading` alongside `user`, guard any effect that clears state with `if (authLoading) return;` before the `if (!user)` branch (so "don't know yet" leaves existing/initial state alone instead of actively clearing it), and change any render condition from `!user ? <LoginPrompt/>` to `!authLoading && !user ? <LoginPrompt/>` so the loading skeleton shows instead of a false "you're logged out." Follow this same three-branch shape (`authLoading` → skeleton, `!user` → login prompt, else → real content) for any new page or context that reads `user` to decide what to render — a plain `!user` check is very likely wrong. `/profile` already had this right (built correctly the first time); `project_folder/[project_id]/page.tsx` never needed it since it fetches via `authFetch()` directly (which resolves the session token itself, independent of this React state) and has no `!user`-gated view.
- **Characters/Style Templates are the reference pattern for new library resources**: each is `types/<resource>.ts` (interface matching the backend schema) + `components/<resource>/<Resource>Card.tsx` (grid card, edit/delete always visible — no hover-to-reveal) + `components/<resource>/Edit<Resource>CardPopUp.tsx` (create/edit form, remounted via a parent-owned `key` prop on open rather than resetting state in a `useEffect`) + `app/(app)/<resource>/page.tsx` (list/create/edit/delete wiring via `lib/api.ts`'s `authFetch`). Style templates additionally show a `Toggle` (`components/Toggle.tsx`) for `is_default` directly on the card, since only one template can be default at a time — see Domain model notes below.
- **`/style_templates`' Starter Templates catalog**: shown as one big popup card, not an inline section on the page — `components/styletemplates/DefaultStyleTemplateCardPopUp.tsx` follows the same `isOpen`/`onClose`/portal-to-`document.body` shape as `ImageZoomPopUp`/`ConformationMessagePopUp`/`ManualImageGenerationPromptCopyPopUp`/`AddCreditsPopUp`, opened by a "Starter Templates" button in the page header (only shown once the catalog fetch returns something) rather than a collapsible dropdown, and sized `sm:max-w-6xl` — wide enough for its own internal grid to run 4 cards across (`lg:grid-cols-3 xl:grid-cols-4`) at desktop width. The whole catalog (`GET /styletemplates/defaults`) is browsable inside that one popup: every entry renders as a card (image, aspect-ratio/scene-density badges, best-for, an `image_prompt` excerpt, its own "Add to Library" button) in that grid inside the popup's scrollable body — there's no second, per-entry popup or drill-down. A card's demo image is clickable to open the shared `ImageZoomPopUp` for a full pinch/scroll-zoomable view; the whole catalog grid shares one `ImageZoomPopUp` instance (`zoomTarget` state holding `{url, alt}`) rather than one per card. `StyleTemplateCard` (the user's own library grid, same page, same `lg:grid-cols-3 xl:grid-cols-4` 4-across layout) does the same thing independently — its own demo-image button opens its own `ImageZoomPopUp` instance — so both card families support the same "click image to zoom" interaction even though only the catalog card exposes a second, deeper popup. Deliberately visually distinct at a glance regardless: catalog cards carry a violet border and a "Starter" ribbon on the image plus the "Add to Library" action; owned cards carry edit/delete/set-default controls and no ribbon. Both `DefaultStyleTemplateCardPopUp`/`StyleTemplateCard` render media in a fixed 16:9 box regardless of the template's own aspect ratio — a 9:16 template is letterboxed inside it (`object-contain`) over a blurred, scaled-up copy of itself (`object-cover blur-xl`) filling the rest of the box, rather than shrinking the box to 4:3, which used to make 9:16 cards a different height than 16:9 ones in the same grid and shift every card's footer out of alignment. The catalog fetch itself runs once on mount and is **not** keyed on `user`, since the endpoint needs no token and a signed-out visitor should see it; a failure is swallowed silently rather than alerting, because the catalog is adjacent to the page's real content. `importedSlugs` (passed down to the popup for the sticky "Added — add again" button state plus an "In library" badge on the card image) is **derived, not tracked as its own state** — `page.tsx`'s `IMPORT_MATCH_FIELDS` lists the exact fields `defaults.py`'s `import_default_style_template()` copies verbatim from a catalog entry (`_IMPORTABLE_FIELDS`) — **`demo_image_url` is deliberately not among them and must not be added back**, since the import now makes a per-user Cloudinary copy and the URL therefore differs from the catalog's on every import, which would make the badge never match — and `matchesDefault()` flags a catalog slug as imported whenever any of the user's own `templates` still matches a catalog entry on every one of those fields. That's what makes the badge survive a page reload with no dedicated DB column or extra fetch: it's re-derived from `templates` (already fetched) and `defaults` (already fetched) every render via `useMemo`. It also means the badge is a live fact, not a sticky flag — editing an imported copy's name or a prompt breaks the field match and the catalog card reverts to "Add to Library," which is correct: at that point it genuinely isn't the unmodified starter template anymore, and re-"importing" would create an independent second copy same as always. Each catalog card's demo image also tracks its own load state (`loadedSlugs`, a `Set<string>` keyed by slug, `onLoad` on the `Image`) — while a real `demo_image_url` is still fetching, the media box shows a spinner over the same neutral background the true "no `demo_image_url`" state uses, rather than that background alone, so a loading image and a genuinely absent one don't briefly look identical; the image fades in via an opacity transition once it finishes loading.
- **`/characters`' Starter Characters catalog**: `components/characters/DefaultCharacterCardPopUp.tsx`, a direct port of the Starter Templates popup above — same `isOpen`/`onClose`/portal-to-`document.body` shape, same `sm:max-w-6xl` / `h-[85vh]` sizing, same internal 4-across grid, same violet border + "Starter" ribbon marking a catalog card as visually distinct from an owned `CharacterCard`, same one-shared-`ImageZoomPopUp`-per-grid (`zoomTarget` holding `{url, alt}`), same per-slug `loadedSlugs` spinner-until-`onLoad` treatment, same public-and-unkeyed-on-`user` catalog fetch whose failure is swallowed silently, and the same `defaultsLoading`-gated same-sized skeleton for the header button (see the CLS bullet above). Two deliberate differences from the style-template version: there is **no aspect-ratio filter row** (a character sheet has no aspect ratio of its own, so there'd be nothing to filter on), and `page.tsx`'s `IMPORT_MATCH_FIELDS` for the derived `importedSlugs` badge is only `["name", "description"]` — `character_sheet_url` is deliberately excluded because the import makes a real Cloudinary copy, so the URL differs on every import by design and including it would make the "In library" badge never match. `handleImportDefault` likewise doesn't clear any other card's `is_default` the way the style-template import does, since a character import is never auto-defaulted server-side (see the backend bullet).
- **Style-template share/download/import** (`lib/styleTemplateShare.ts` + `lib/styleTemplateImport.ts`, wired into `StyleTemplateCard.tsx`'s Download/Share icon buttons and `style_templates/page.tsx`'s "Import" header button + hidden file input): a style template exports as the same portable JSON shape `DefaultStyleTemplate` already uses (`buildShareableStyleTemplate()` — no `id`/`user_id`/`is_default`/timestamps, a cosmetic `slug` derived from the name), so it can be handed to another user, who imports it back via `POST /styletemplates/create` after strict client-side validation (`parseStyleTemplateImport()`, throwing `StyleTemplateImportError` on the *first* problem rather than coercing: required fields non-empty, word/char ceilings matching `EditStyleTemplateCardPopUp.tsx`'s own limits, `scene_density` in `{small,medium,high}`, `image_aspect_ratio`/`video_aspect_ratio` each `16:9`/`9:16` *and* equal to each other since the app only ever offers one picker for both, `demo_image_url` a well-formed URL if present). Download saves a `.json` file directly via a synthetic `<a download>` click. Share uses the Web Share API to open the native OS share sheet (WhatsApp/Gmail/Bluetooth/whatever's registered) — but the shared *file* attachment is packaged as `.txt`/`text/plain`, not `.json`/`application/json`: Chromium/WebKit's file-sharing implementation only allows attaching files whose extension is on a fixed safe-list (images/audio/video/PDF/plain-text/common office docs), which does not include `.json`, so `canShare({files:[...]})` on a `.json` file always returns `false` and silently falls through to a plain download — indistinguishable from clicking Download, which is exactly the bug this works around. The content is byte-identical either way since `parseStyleTemplateImport()` never inspects the file extension, which is also why the Import file input's `accept` lists both `.json` and `.txt`/`text/plain`. If file-sharing isn't supported at all, `shareStyleTemplateJson()` falls back to a **text** share (Level 1 of the Web Share API — title/text/url, no files, no type restriction) before finally giving up and downloading, so Share only silently degrades to Download on a browser with no `navigator.share` whatsoever.

- **Shared live credit balance** (`context/CreditBalanceContext.tsx`, mounted in root `layout.tsx` inside `AuthProvider`): every component that reads or spends credits — `Navbar.tsx`, `generate_script/page.tsx`, both Generate popups, `GeneratedScriptFeedbackPopUp.tsx`, `SceneCard.tsx`, `VideoMetaDataCard.tsx`, `/profile`'s Razorpay success handler — shares one `balance` via `useCreditBalance()` instead of each fetching/holding its own copy. Follow this pattern (consume the shared context, don't add a new local `balance` state) for any future credit-spending feature. Three methods, matching the backend's reserve-first model: `reserveBalance(cost)` subtracts as a generation *starts* (the backend has already reserved it by then, so the pill would otherwise overstate what the user has — and it must be a functional state update, since several scene cards can start at once and `setBalance(balance - cost)` off a captured `balance` loses all but the last); `setBalance(data.credits_remaining)` reconciles against the authoritative number every AI/payment response carries; `refreshBalance()` re-fetches `GET /users/me`, used for each flow's pre-submit staleness check and after a cancel or error, where only the backend knows whether a refund happened. Cost constants for the optimistic subtraction live in `lib/credits.ts` and must stay numerically in sync with the backend's — drift is self-correcting (every call settles on `credits_remaining`) but visible until then.
- **`/profile`**: the account header (avatar/name/email/balance + "Add Credits" → `AddCreditsPopUp` → Razorpay) plus `components/profile/PaymentAndUsageHistoryTabCard.tsx`, one component owning both README §`/profile` tabs. Each tab fetches **once on first visit** and caches in component state, so switching tabs doesn't re-hit the backend; the cache is invalidated by the page remounting the card with a bumped `key` after a successful top-up (the same parent-owned-`key` trick `AddCreditsPopUp` uses — namespaced `history-${historyKey}` rather than the bare counter, since a bare `0` collides with `popupKey`'s own `0` as siblings in the same children array). `loading` is *derived* (`!data && !error`) rather than stored — a stored one would have to be set synchronously inside the fetch effect for the already-cached case, which is exactly what eslint's `react-hooks/set-state-in-effect` rejects; errors are held per-tab so one tab failing doesn't blank the other, and a failed tab waits for an explicit "Try again" instead of refetching on every tab switch. The effect that fetches the profile is keyed on `user?.id`, not the `user` object — `AuthContext` hands out a fresh session (and so a fresh `user` reference) on every token refresh and window focus, which used to re-run the effect, flip `loading`, and unmount+remount `PaymentAndUsageHistoryTabCard` on a timer having nothing to do with the user actually changing, discarding its selected tab and fetch cache each time. Rows whose `project_exists` is true link to `/project_folder/{id}`; the rest get a muted "deleted" badge. The trailing credit chip is also a `<button>` that toggles that popover, so the breakdown is reachable by tap and keyboard rather than hover-only.

Only `GeneratedScriptFeedbackPopUp.tsx` (the Improvise feedback prompt), `ShowScriptTemplatesCardPopUp.tsx` (browsing saved `script_templates` to re-import into the form — has an `onDelete` callback so the page can clear its session state if the currently-active template gets deleted), and `ConformationMessagePopUp` (generated-script delete confirmation, same component `characters/page.tsx` uses) are actual portaled popups. Four menu buttons open `ChooseCharacterPopUp`/`ChooseStyleTemplatePopUp`/`VoiceOverControllerPopUp`/`AdvancedSettingsPopUp` (all in `components/projectfolder/`, following the same portaled-popup shell as `EditCharacterCardPopUp.tsx` etc.); each popup's `onSaved`/`onImported` callback pushes the updated `Project` straight back into the page's local state rather than triggering a re-fetch. There's deliberately no "copy all images" button — multi-item `navigator.clipboard.write()` isn't reliably supported across browsers, so the user copies one character at a time. That per-image copy goes through `lib/download.ts`'s `copyImagesToClipboard()`, new alongside `downloadAsset()`: it normalizes any fetched image to `image/png` via an offscreen canvas (the one MIME type all major browsers' Clipboard API reliably accepts for images) and passes each `ClipboardItem` a `Promise<Blob>` rather than an already-resolved one, so the `navigator.clipboard.write()` call itself stays synchronous within the click handler's call stack — required for Safari/Firefox to still recognize it as a real user gesture despite the async fetch/convert work happening after. `SceneCard.tsx` owns its own image/animation generation calls (and their `AbortController`-based Cancel buttons) internally rather than lifting that state to the page, calling `useCreditBalance().setBalance()` directly on success — same "consume the shared context, don't thread it through props" rule as the rest of the app. One deliberate exception: image-generation *concurrency* is capped at 5 at a time across the whole page (both `SceneCard`'s own Generate button and "Generate All Images (Automatic)" below), and that shared slot pool (`tryAcquireImageSlot`/`releaseImageSlot`, plain `useRef` counters in `page.tsx`) is threaded into `SceneCard` as props, not context — only these two call sites need it, so a page-scoped context would be pure ceremony; a click that can't get a slot calls `onImageConcurrencyLimitReached` to show an `AlertMessagePopUp` warning instead of firing the request. Stopping it aborts every in-flight request via per-scene `AbortController`s *and* calls `POST /projects/scenes/cancel_generation` for each — matching `SceneCard`'s own Cancel button — so a stopped run can't keep generating (and saving) in the background after the user gave up on it; nothing already reserved is refunded. `ManualImageGenerationPromptCopyPopUp.tsx` (opened by "Generate All Images (Manual)") is the free/manual counterpart: a pure copy tool, no generation call of its own — see the backend architecture bullet above for where its flat per-scene charge actually happens. Clicking a generated scene image (or the `VideoMetaDataCard.tsx` thumbnail) opens the shared `ImageZoomPopUp`; clicking a generated animation opens `VideoPlayingCardPopUp.tsx` (a full-screen player with its own download button) — the small inline preview `<video>` deliberately has no `controls`/is `pointer-events-none` so a click always opens the popup instead of fighting the browser's native play/seek controls. A failed download throws `AssetUnavailableError` (carries the HTTP status) so the UI can say the host refused the file (e.g. a disabled Cloudinary account returns 401 on every asset) rather than silently redirecting to a dead page. `VideoMetaDataCard.tsx`'s thumbnail also has its own collapsible, autosave-on-blur `thumbnail_prompt` editor (toggled via a blue "Prompt" link) — independent of the card's Title/Description/Tags fields, which still require the explicit "Save Metadata" click; editing the prompt changes what the next "Regenerate Thumbnail" click actually generates (see `ProjectUpdate` schema note above). **`SceneCard.tsx`'s image/animation preview boxes double as drop targets**: dragging a file onto either (or clicking a small "Upload" button next to Generate/Regenerate) uploads it via `upload_scene_image`/`upload_scene_animation` — free, no credit cost. A trash-icon button next to each asset's download button opens `ConformationMessagePopUp` (destructive) before calling the matching `DELETE .../image`/`.../animation` endpoint. Primary path is the **File System Access API** (`showDirectoryPicker`, Chrome/Edge only) writing real files into a real chosen folder (`images/`, `animation/`, thumbnail at the folder root); `src/types/file-system-access.d.ts` adds the one ambient declaration TypeScript's bundled `lib.dom.d.ts` is missing (`Window.showDirectoryPicker` itself — the handle types it returns are already there). Where that API is unavailable, `runProjectDownload()` falls back to building the identical folder structure as a single `.zip` (`lib/zip.ts` — a from-scratch, dependency-free STORE-only zip writer, since the source files are already-compressed images/video and deflating them again would spend CPU for near-zero savings) and triggering a normal browser download; the button's tooltip says which path a given browser gets. `buildDownloadTasks()` computes the full task list up front (so the button can show a file count and disable itself instead of opening an empty folder picker when nothing's been generated yet) and zero-pads scene numbers to the project's own scene count. Fetching runs through a small concurrency pool (`runPool()`, 4 at a time — Cloudinary is the bottleneck, not local CPU) sharing one `AbortController` for the whole run, so Stop cancels whatever's currently in flight immediately rather than only stopping new fetches from starting; an aborted fetch is counted as *cancelled*, not *failed*, in the end-of-run summary. **Voiceover is deliberately absent** — nothing generates `project_voiceovers` rows yet (see the voiceover bullet below), so there's nothing to add a task for; the module's own docstring notes that adding those tasks later is additive, not a restructuring, since `runPool`/`downloadToDirectory`/`downloadToZip` are already category-agnostic.

## Domain model notes (see `vgaidatabase.dbml` for full schema)

- **Credits are the app's currency**: `100 credits = $1`. All AI actions (LLM, image, animation, voiceover, and one-off "miscellaneous" generations like character-sheet/style-template/script generation) are billed in credits against `users.current_credit_balance`. Script generation's cost isn't flat — it scales with the chosen `script_word_length` band (`ceil(upper_bound / WORDS_PER_CREDIT)`, `WORDS_PER_CREDIT = 30` in `viralscripttopicresearch.py` — the `ceil()` matters since 30 doesn't evenly divide every 100-word band), while topic research is a flat 5 credits regardless of inputs. Manually editing/deleting a `generated_scripts` row is free (no AI call). Project-scoped generation is billed the same currency but tracked separately (see `project_expence_tracker` bullet below): automatic scene-splitting is `ceil(script_word_count / 10)` credits (`WORDS_PER_CREDIT_AUTO` in `paidscripttoscenesplitter.py`), scene/thumbnail image generation is a flat 4 (`"base"`)/20 (`"pro"`) credits (`imagegeneration.py`), animation generation is a flat 20 (`"base"`, Wan 2.6, 5s)/40 (`"pro"`, Veo 3.1 Lite, 6s) credits (`animationgeneration.py`, `app/openrouter_video.py`). Manually editing/deleting/creating a `scenes` row is free, and so is manually uploading or deleting a scene's image/animation asset (`generatedscenecard.py`'s upload/delete endpoints — no AI call happens on that path at all). The one exception to "editing a scene's prompts is free" is AI-assisted prompt rewriting: `imageregeneration.py`'s `REWRITE_CREDIT_COST = 1` flat fee applies both to syncing the animation prompt to a hand-edited image prompt and to the prompt-rewrite step "Regenerate" now runs before generating (on top of which the normal per-tier image cost above still applies).
- **Credits are reserved, not charged on success**: see the backend bullet of the same name. Costs are unchanged; what changed is *when* they leave the balance (before the provider call) and what happens on cancel (charged, result discarded).
- **Snapshotting pattern**: when a project imports a character or style template, the data is copied into project-scoped tables/columns (`project_characters`, `projects.snapshot_styletemplate_*`) rather than referenced live — later edits to the library item must not retroactively change existing projects. `projects.snapshot_styletemplate_*` snapshots **8** style-template fields, not just the 5 you'd expect from name/prompts/description — `image_aspect_ratio`/`video_aspect_ratio`/`scene_density` are snapshotted too (3 columns added specifically for `paidscripttoscenesplitter.py`/`imagegeneration.py`/`animationgeneration.py`, which need them at generation time and can't read them live off `style_templates` per this same snapshot rule) — keep `vgaidatabase.sql`'s `alter table` backfill block and `vgaidatabase.dbml` in sync if a 9th field is ever added. `project_characters` intentionally has **no** `character_id` FK back to `characters` (a real copy, not a reference), and as of the character-import fix, `snapshot_character_sheet_url` is a real copy too — import (`import_project_characters()`, and `create_project()`'s default-character auto-import) now calls `copy_image_from_url()` to upload an independent Cloudinary asset under `<project_id>/project_characters/` rather than reusing the character's `characters/` URL, so deleting or editing the library character can never touch a project that already imported it. `snapshot_character_sheet_url` can also be replaced later via a project-scoped edit (`PUT /projects/{id}/characters/{project_character_id}`, see the `/project_folder` pattern bullet and Frontend architecture's "Editing an imported snapshot" bullet), landing in the same folder either way. `_owns_project_character_image()` still guards every `delete_media()` on this column — every row in the DB is confirmed to already own its image copy (the single pre-fix row was migrated by a one-time backfill script, since removed), so the guard is currently unused in practice but stays in place as cheap insurance against a restored backup or another environment reintroducing an old-style row.
- **Spend history survives deletion by design**: `project_expence_tracker` stores `project_id`/`project_name` with no foreign key specifically so a project's credit-spend history remains queryable (for `/profile` usage history) after the project itself is deleted. In practice there's exactly one `project_expence_tracker` row per project (`projectcrud.py`'s `_add_project_expense()` fetches-or-creates it and increments one of `llm_credit_spent`/`image_credit_spent`/`animation_credit_spent`/`voiceover_credit_spent`), not one row per spend event — it's a running per-project total, not a transaction log.
- **`is_default` cardinality differs by table**: `characters` has no uniqueness constraint, so a user can mark multiple characters default. `style_templates` has a partial unique index (`idx_user_default_style`, `WHERE is_default = true`) enforcing at most one default per user — the route layer must unset any existing default before setting a new one (see `_clear_existing_default()` in `styletemplates/crud.py`) or the DB write fails.
