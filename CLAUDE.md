# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

**vgAI** is an AI video-production SaaS: creators paste a script, split it into scenes, and generate matching images/animations/voiceovers per scene, reusing saved character and style-template libraries. Full product spec (all pages, features, and the credit system) is in [`README.md`](./README.md) — read it before implementing any feature, it's the source of truth for intended behavior. The full DB schema is in [`vgaidatabase.dbml`](./vgaidatabase.dbml).

**Current state: early build, not just scaffold anymore.** Auth (Supabase Google OAuth, an inline `LoginModal` gating write actions rather than a forced login redirect) and three full CRUD library features are implemented end-to-end, backend route + Pydantic schema + frontend page/card/edit-popup: **Characters** (`/characters`), **Style Templates** (`/style_templates`), and **Generate Scripts** (`/generate_script`, `script_templates` + `researched_topics` + `generated_scripts`). Characters and Style Templates each have their "Generate with AI" flow fully built (see AI-generation pattern below) — **not Gemini as originally spec'd in `README.md`**, both use OpenAI (LangChain `ChatOpenAI` for text/structured output, `gpt-image-2` for character sheet images) via `app/openai_client.py`. Style Templates' create/edit form and its "Generate with AI" flow are both aspect-ratio-aware (`16:9` long-video vs `9:16` Reels, a single picker driving both `image_aspect_ratio`/`video_aspect_ratio` and, on the generate path, a distinct system-prompt creative brief per format — see AI-generation pattern below). `/generate_script` is a different, multi-step AI flow — research 10 viral topics (Perplexity `perplexity/sonar-pro`) → generate a full script + character list per chosen topic (Claude `anthropic/claude-sonnet-5`) → optional feedback-driven "Improvise" regeneration, all fully DB-backed and persisted (see `/generate_script` AI pattern below) — unlike Characters/Style Templates' accept-or-reject-into-`create` pattern, research/generation here writes to the DB immediately as it happens, with no separate save step; only the reusable form-input preset (`script_templates`, gated by `is_saved`) still needs an explicit "Save as Template" click. Generated-script cards support inline edit and delete, and the "Import" button creates a new `/project_folder/{project_id}` project pre-filled with that script (see below) rather than being a placeholder. Credit top-ups are also implemented end-to-end via Razorpay (`app/routes/payments/crud.py` — order creation + Checkout-signature verification; `app/routes/payments/webhook.py` is a documented, not-yet-registered backup path, see its docstring). The Navbar's credit-balance pill is live app-wide via a shared `CreditBalanceContext` (see Frontend architecture below) — spending credits anywhere updates it instantly, not just on next page load. Navbar and Sidebar are real chrome (not placeholders — see Frontend architecture below). The home page (`/`) also still has leftover demo-popup buttons (Interactive Components section) from the original template — not a real feature, safe to delete when that section of the app gets built. Don't assume a feature exists in code just because it's documented in `README.md`; check the actual route/component first — `README.md`'s Tech Stack/§5 still says Gemini for the Characters/Style Templates flows, which is now stale.

**`/project_folder/{project_id}` — also now built, but only its first slice.** Project-folder CRUD is wired from the sidebar (`Sidebar.tsx`'s Project Folders section — create/rename/delete, live everywhere via `ProjectsContext`) and the workspace page itself (`app/(app)/project_folder/[project_id]/page.tsx`) supports: pasting/autosaving a script, importing characters/a style template (`ChooseCharacterPopUp.tsx`/`ChooseStyleTemplatePopUp.tsx`, snapshotted the same way `POST /projects/create` auto-imports the user's default character(s)/style template on project creation), saving ElevenLabs voiceover *settings* (`VoiceOverControllerPopUp.tsx` — settings only, no TTS call yet), picking `llm_model_id`/`image_model_id`/`animation_model_id` tiers (`AdvancedSettingsPopUp.tsx`), and **"Generate Scenes (Automatic)"** — a single structured LLM call (`app/routes/project/paidscripttoscenesplitter.py`, `gpt-4o` for `"base"`/`gemini-3-pro-preview` for `"pro"` via `app/gemini_client.py`) that replaces the project's scene batch outright and writes video metadata (title/description/tags/thumbnail prompt) onto the `projects` row. Each `SceneCard.tsx` can then generate its own image (`app/routes/project/imagegeneration.py`, `gpt-image-2`, multi-image `images.edit` reference call when the scene has involved characters) and, once an image exists, its animation (`app/routes/project/animationgeneration.py`, `alibaba/wan-2.6` for `"base"`/`google/veo-3.1-lite` for `"pro"` via OpenRouter's video API, `app/openrouter_video.py`'s long-running-job polling) — and `VideoMetaDataCard.tsx` can generate the video thumbnail the same way. **"Generate Scenes (Manual)" and "Generate Voiceover" are deliberately unwired** — visible as disabled buttons on the page, their backend files (`app/routes/project/freescripttoscenesplitter.py`, `app/routes/project/voiceovertts.py`) exist as empty stubs, not yet registered in `router.py`. See the Backend/Frontend architecture bullets below for the actual patterns, which diverge from `README.md`'s original single-Gemini-call description of automatic scene generation.

## Backend architecture

- **Routing**: `app/main.py` creates the `FastAPI` app and mounts `app/routes/router.py`'s `api_router`, which aggregates per-resource routers (`app/routes/users.py`, `app/routes/characters/crud.py`, `app/routes/styletemplates/crud.py`, `app/routes/scriptgenerationtemplate/crud.py`, `app/routes/payments/crud.py`, `app/routes/project/*.py`). Multi-endpoint resources live in their own subpackage (`app/routes/<resource>/crud.py` + `generate<resource>.py`). Add new resources the same way, and register the router in `router.py`.
- **AI-generation pattern** (`characters/generatecharacter.py`, `styletemplates/generatetemplate.py`): both `POST .../generate` endpoints follow the same shape — check `current_credit_balance` against a fixed per-call cost up front (402 if insufficient), call OpenAI, deduct credits + bump `miscellaneous_credit_spent` on success, and return the generated draft *unsaved*. The frontend shows an accept/reject preview (`GenerateCharacterSheetPopUp.tsx`, `GenerateStyleTemplatePopUp.tsx`); accepting re-submits the (possibly-edited) draft to the resource's normal `POST .../create` endpoint — generation never writes to the DB directly. `generatetemplate.py` also hard-truncates every generated field to its word-count ceiling after the LLM call, since prompting for a limit isn't a guarantee and an over-limit draft would fail `EditStyleTemplateCardPopUp.tsx`'s own validation on save/edit — keep those ceilings numerically in sync if either side changes. `generatetemplate.py` also builds its system message per-call via `_build_system_message(aspect_ratio)`, injecting one of two `VIDEO_FORMAT_BRIEFS` (long-form vs Reels) so the chosen aspect ratio actually changes what the AI writes (pacing/hook style), not just the saved metadata — keep the frontend's `ASPECT_RATIO_OPTIONS` and this dict's keys in sync. Both use OpenAI via `app/openai_client.py` (LangChain `ChatOpenAI` for text/structured-output, `gpt-image-2` for character-sheet images, `quality="low"`/`"high"` gated behind a "Generate with Pro" toggle on the character flow) — not Gemini, despite `README.md`. The backend balance check is the authoritative guard, but both Generate popups also call a `refreshBalance()` helper right before submit (re-fetches `GET /users/me`, aborts client-side with an error if now insufficient) — the balance shown on popup-open can go stale if the user's credits changed elsewhere (another tab, a top-up) while it sat open, and this avoids the wasted round-trip of hitting `/generate` only to get a 402 back.
- **`/generate_script` AI pattern** (`scriptgenerationtemplate/viralscripttopicresearch.py` + `crud.py`, both under the shared `/scripttemplates` prefix — routers registered in that order in `router.py` specifically so `viralscripttopicresearch`'s literal paths like `/generatedscripts` aren't shadowed by `crud.py`'s dynamic `/{scripttemplate_id}`): unlike the AI-generation pattern above, this flow is **fully DB-backed as it happens** — there's no accept/reject-into-`create` step, every successful call writes straight to `researched_topics`/`generated_scripts`. `/generatetopics` (Perplexity `sonar-pro`, flat `TOPIC_RESEARCH_CREDIT_COST` of 5) either creates a fresh `script_templates` row (`is_saved=false`, when the request has no `script_template_id`) or updates an existing one's fields, then **upserts** 10 `researched_topics` rows keyed on `(script_template_id, topic_number)` — so re-researching the same session updates those same 10 rows in place instead of accumulating. `/generatescript` and `/improvise` (both Claude `sonnet-5`, cost = `ceil(script_word_length's upper bound / WORDS_PER_CREDIT)`, `WORDS_PER_CREDIT = 30`, e.g. an "800-900" band costs 30 credits) only take `{script_template_id, topic}` / `{generated_script_id, feedback}` — every other field (category, descriptions, country, word length) is read back from the DB row, never re-trusted from the client, and `/generatescript` inserts a new `generated_scripts` row while `/improvise` updates one in place via `_get_owned_generated_script()`. `PUT`/`DELETE /generatedscripts/{id}` let a user manually edit or remove a generated script directly (no AI call, no credit cost). `GET /generatedscripts` returns *all* of a user's generated scripts globally (not scoped to one session) so they survive across page reloads; `GET /{id}` and `GET /{id}/topics` (both in `crud.py`) let the frontend restore a session's form state + topics after a reload. Characters are stored on `generated_scripts.character_involved` as delimited text — `|||` between characters, `::` between each character's fields (`_serialize_characters()`/`_parse_characters()`) — deliberately not `#`/`,`, which can plausibly appear inside AI-generated names/descriptions. Same balance-check-then-deduct shape as the AI-generation pattern above (`_check_and_get_balance()`/`_deduct_credits()` helpers). Both LLM calls go through `app/openrouter_client.py`'s `get_openrouter_chat_model()` (`ChatOpenAI` pointed at OpenRouter's `base_url`, same class as the OpenAI flows) — Claude calls use `.with_structured_output()`; the Perplexity call does not (uncertain tool-calling support), so `/generatetopics` instead prompts for raw JSON and parses it defensively (`_parse_topics_json()`, strips code fences / extracts the first `[...]` block) rather than trusting structured output. `script_templates.is_saved` distinguishes an explicit "Save as Template" (`POST /create`, `is_saved=true`, shown in "My Templates") from the auto-created row behind a research/generate session (`is_saved=false`, invisible to `GET /` which filters on `is_saved=true`) — `POST /create` reuses the session's row (via an optional `script_template_id` in the payload) instead of inserting a duplicate when one already exists.
- **Payments**: `app/routes/payments/crud.py` implements Razorpay credit top-ups — `POST /payments/create-order` creates a Razorpay order + a `pending` `credit_topups` row priced off a fixed `PAISE_PER_CREDIT` (INR-only; see its module comment for why), `POST /payments/verify` verifies the Razorpay Checkout signature and applies the credits. `app/routes/payments/webhook.py` is a written-but-unregistered backup path for the case where a payment succeeds but the user closes the tab before `/verify` fires — see its docstring for why it's inactive (needs a real deployed domain) and how to turn it on.
- **`/project_folder` pattern** (`app/routes/project/`, 5 registered files + 2 unregistered stubs): `projectcrud.py` owns the `projects`/`project_characters` resources (`GET/POST/PUT/DELETE /projects/...`, `.../characters/...`, `.../styletemplate/import`, `.../voiceoversettings`) and exports the helpers every other file in this package imports — `_get_owned_project()` (same ownership-check shape as `characters/crud.py`), `_check_project_balance()`/`_deduct_project_credits()`. That deduct helper is the key departure from the AI-generation pattern above: project-scoped spend (script-splitting, image, animation) increments a *running per-project* `project_expence_tracker` row (`_add_project_expense()`, fetch-or-create-then-increment, one row per project) instead of `users.miscellaneous_credit_spent`, per README §2's per-project-vs-miscellaneous split. `paidscripttoscenesplitter.py` (`POST /projects/scenes/generate_automatic`) is the "Generate Scenes (Automatic)" call: one structured-output LLM call (`gpt-4o` for `"base"`, `gemini-3-pro-preview` via `app/gemini_client.py`'s `get_gemini_chat_model()` for `"pro"`) given the style-template snapshot + project characters (name/description only) + full script, returning `scenes[]` + `metadata` + `compact_image_prompt`/`compact_animation_prompt` — the compact fields are prepended in Python (`f"{compact}. {scene_prompt}"`) before persisting, which is why `scenes.scene_image_prompt`/`scene_animation_prompt` have no separate compact-prompt columns. A regenerate call deletes the project's existing scenes (cleaning up their Cloudinary assets first) and inserts a fresh batch, scene numbers always re-sequenced 1..N in Python regardless of what the LLM returned. `imagegeneration.py` (`POST /projects/image/generate_and_save`, `/generate_thumbnail_and_save`) and `animationgeneration.py` (`POST /projects/animation/generate_and_save`) generate a scene's image/animation or the project's thumbnail — image generation uses `openai_client.images.edit()` with a *list* of reference images when the scene/project has involved characters (vs `images.generate()` when it doesn't); animation is the one generation path with real mid-flight cancellation, since `openrouter_video.generate_video_from_image_url()`'s job-polling loop checks `await request.is_disconnected()` each iteration and bails without saving/charging if the client (Cancel button) disconnects — image/thumbnail generation can't do this (a single blocking provider call), so their "Cancel" is frontend-only (`AbortController`, resets the loading state but a request that finishes server-side after cancel still saves + charges). Animation passes the scene's already-hosted Cloudinary image URL straight through as OpenRouter's `frame_images` input (no download/re-upload needed, unlike the multi-character-reference image path above). `generatedscenecard.py` is plain scene CRUD (`GET/POST/PUT/DELETE /projects/scenes/...`, no AI call, no credit cost — reordering via `scene_number` is out of scope). `freescripttoscenesplitter.py` (manual/paste-from-gemini.com scene splitting) and `voiceovertts.py` (voiceover generation) are empty, unregistered stubs — deliberately deferred, see the Current-state note above.
- **Config**: `app/config.py` defines a `pydantic-settings` `Settings` class loaded from `backend/.env`, exposed as a module-level singleton `settings`. `env.example` at the backend root is stale — it references an unrelated prior project's variables (`DATABASE_NAME`, `MAX_BULK_URLS`, `DOWNLOADS_DIR`) and does not match what the code actually reads.
- **Gemini**: `app/gemini_client.py` wraps `langchain_google_genai.ChatGoogleGenerativeAI` (`get_gemini_chat_model()`) solely for the "pro" `llm_model_id` tier's structured scene-splitting output. Needs `GEMINI_PAID_API_KEY` (already in `.env`, exposed on `Settings`). It previously also drove animation generation via the raw `google-genai` SDK's Veo long-running-operation flow — that path was removed in favor of routing animation through OpenRouter like every other project-scoped provider call (see the next bullet); don't reintroduce a `google-genai` dependency for animation.
- **OpenRouter video (animation)**: `app/openrouter_video.py` is a raw `httpx`-based client (not LangChain, since this is OpenRouter's async video-job REST API, not a chat completion) for `animationgeneration.py`'s image-to-video calls — `POST {OPENROUTER_BASE_URL}/videos` with the scene's existing Cloudinary image URL as a `frame_images` first-frame reference, then polls the returned `polling_url` until `status` is `completed`/`failed`, downloading the result from `unsigned_urls[0]`. Resolves `animation_model_id` to a real OpenRouter model id + clip duration: `"base"` → `alibaba/wan-2.6`, 5s; `"pro"` → `google/veo-3.1-lite`, 6s (`ANIMATION_BASE_MODEL`/`ANIMATION_PRO_MODEL`/`*_DURATION_SECONDS` constants) — `animationgeneration.py` pairs these with its own credit costs (20/40). Reuses `app/openrouter_client.py`'s `OPENROUTER_BASE_URL` and `settings.OPENROUTER_PAID_API_KEY`, the same key already used for `/generate_script`'s Perplexity/Claude calls — no new env var needed.
- **Cloudinary**: `app/cloudinary.py` provides `upload_image()`/`delete_media()` helpers (config fields for cloud name/API key/secret/folder are declared on `Settings`), plus `upload_image_bytes()`/`upload_video_bytes()` (both thin wrappers over a shared `_upload_bytes()`) for content that arrives as raw bytes rather than an `UploadFile` — OpenAI's base64 scene/thumbnail images, OpenRouter's raw video bytes. Assets upload to `<CLOUDINARY_FOLDER_NAME>/<user_id>/<resource>/...`; see `README.md` §9 for the full planned folder layout — `characters/` and the `<project_id>/{scene_images,scene_animation,thumbnail_image}/` slices are wired up now, `project_characters`/`voiceovers` are not (voiceover generation is still a stub, and `project_characters.snapshot_character_sheet_url` deliberately copies the character's existing URL rather than re-uploading — never `delete_media()` it, that would delete the still-live character-library asset). `delete_media()` is best-effort (swallows errors) since a Cloudinary asset already gone shouldn't block a DB delete.
- **Supabase**: `app/supabase.py` exports a singleton `supabase` client built with the *secret* (service-role) key — it bypasses Row Level Security, so any per-user access scoping has to be enforced in route code, not assumed from RLS. The `_get_owned_<resource>` helper pattern in `characters/crud.py`/`styletemplates/crud.py`/`project/projectcrud.py` (fetch by id, 404 if missing or `user_id` mismatch) is how that scoping is done — follow it for new resources. `project/generatedscenecard.py`'s `_get_owned_scene()` is the same idea one level down (scenes have no `user_id` column, so it checks ownership via the parent project).
- **Schemas**: request/response models live in `app/schemas/*.py` as plain Pydantic models per resource. `character.py`, `styletemplate.py`, and `payment.py` are aligned to their DBML tables (plus the two `Generate*Request`/`Generate*Response` pairs for the AI-generation endpoints, which aren't DB-backed). `scripttemplate.py` is fully DB-backed (unlike the other two `Generate*` pairs) — `ScriptTemplate`/`Create`/`Update` map to `script_templates`, and `TopicResearchResponse`/`ScriptGenerateResponse`/`ScriptImproviseResponse`/`GeneratedScriptRecord` all round-trip through `researched_topics`/`generated_scripts`, not just describe an ephemeral draft. `project.py`/`scene.py` map to `projects`/`scenes` the same fully-DB-backed way; `ProjectUpdate` is the one schema in the codebase using `model_dump(exclude_unset=True)` partial-update semantics rather than full-replace, since rename/script-autosave/model-tier-pick/thumbnail-prompt-autosave are separate UI surfaces each touching different fields — `thumbnail_prompt` in particular is read straight off the `projects` row by `imagegeneration.py`'s thumbnail endpoint at generation time, so editing it via `VideoMetaDataCard.tsx`'s autosave-on-blur field (see Frontend architecture below) is enough to change what the next "Regenerate Thumbnail" click actually generates, with no other backend change needed.

## Frontend architecture

- **App Router + client-heavy pages**: routes live under `frontendweb/src/app/`. Existing pages so far use `"use client"` liberally (see `page.tsx`); shared chrome lives in `frontendweb/src/components/`.
- **Layout shell**: `layout.tsx` wraps every page in `ThemeProvider` → `SplashScreen` + `MainLayout`. `MainLayout` renders `Sidebar` + `Navbar` + page content + `Footer`, and owns the mobile sidebar open/close state (sidebar is an off-canvas drawer below `md:`).
- **Theme**: dark mode is a `dark` class on `<html>`, decided pre-hydration by an inline script in `layout.tsx` (reads `localStorage.theme`, falls back to `prefers-color-scheme`) to avoid a flash of the wrong theme. `ThemeProvider` (`components/ThemeProvider.tsx`) mirrors that into React state after mount and exposes `useTheme()`/`toggleTheme()` for interactive toggling; keep both in sync if you touch theme logic.
- **Sidebar/Navbar match the README spec**: `Sidebar.tsx` implements the `README.md` §4 structure — a Library section (Characters, Style Templates, Generate Scripts, Liked Projects) that's always visible/clickable even when logged out, and a Project Folders section that shows a login-gated message instead of the project list when logged out. When logged in, that section is a live list from `ProjectsContext` (create/inline-rename/delete, same `ConformationMessagePopUp` delete-confirmation pattern as the library pages) rather than a placeholder. `Navbar.tsx` has Home/About/Contact (no login required to view), a credit-balance pill (links to `/profile`) when logged in, and either an account-avatar menu or a "Login" button depending on auth state.
- **Shared project list** (`context/ProjectsContext.tsx`, mounted in root `layout.tsx` next to `CreditBalanceProvider`): holds the lightweight `{id, name}[]` list both `Sidebar.tsx` and `generate_script/page.tsx`'s Import flow need, with `createProject()`/`renameProject()`/`removeProject()` methods that update local state immediately (no extra round-trip) so a rename/delete from either the sidebar or the project page itself stays in sync everywhere instantly — same reasoning as `CreditBalanceContext`. The `/project_folder/{project_id}` page itself does its *own* separate `GET /projects/{id}` fetch for full project detail (script, snapshots, settings) — this context only ever holds `id`/`name`.
- **Public browsing, gated actions**: nothing forces a login redirect on page view — `(app)/layout.tsx` renders `MainLayout` regardless of auth state. Write actions (create/edit/delete/generate) call `requireAuth()` from `AuthContext` (`context/AuthContext.tsx`) first; if signed out, it opens the global `LoginModal` (rendered once from root `layout.tsx`) and returns `false` so the caller bails out. Follow this pattern for any new write action rather than redirecting to `/login`.
- **Characters/Style Templates are the reference pattern for new library resources**: each is `types/<resource>.ts` (interface matching the backend schema) + `components/<resource>/<Resource>Card.tsx` (grid card, edit/delete always visible — no hover-to-reveal) + `components/<resource>/Edit<Resource>CardPopUp.tsx` (create/edit form, remounted via a parent-owned `key` prop on open rather than resetting state in a `useEffect`) + `app/(app)/<resource>/page.tsx` (list/create/edit/delete wiring via `lib/api.ts`'s `authFetch`). Style templates additionally show a `Toggle` (`components/Toggle.tsx`) for `is_default` directly on the card, since only one template can be default at a time — see Domain model notes below.
- **"Generate with AI" popups follow a shared shape**: `components/characters/GenerateCharacterSheetPopUp.tsx` and `components/styletemplates/GenerateStyleTemplatePopUp.tsx` both go form → `generating` loading state (with an estimated wait-time hint) → accept/reject preview of the AI draft → "Accept & Save" re-submits to the resource's normal `POST .../create`, not a separate save path. Both check/display live credit balance (shared `useCreditBalance()`, see below) and disable Generate when the balance is below that flow's fixed cost; keep the frontend's cost constant and the backend's `GENERATE_CREDIT_COST` numerically in sync when either changes — nothing enforces this automatically. The style-template flow also includes the same `ASPECT_RATIO_OPTIONS` picker as its edit popup, sent as `aspect_ratio` in the request. `CreditCoinIcon` (`components/CreditCoinIcon.tsx`) is the one gold-coin glyph used for every credit reference app-wide (Navbar balance pill, `/profile`, `AddCreditsPopUp`, both Generate popups) — use it instead of an icon-library coin so credits read as the same in-app currency everywhere.
- **Shared live credit balance** (`context/CreditBalanceContext.tsx`, mounted in root `layout.tsx` inside `AuthProvider`): every component that reads or spends credits — `Navbar.tsx`, `generate_script/page.tsx`, both Generate popups, `GeneratedScriptFeedbackPopUp.tsx`, `/profile`'s Razorpay success handler — shares one `balance` via `useCreditBalance()` instead of each fetching/holding its own copy. Any successful credit-spending response calls the context's `setBalance(data.credits_remaining)` directly (no extra round-trip, since every AI/payment endpoint already returns the new balance) so the Navbar pill updates instantly regardless of which page triggered the spend; `refreshBalance()` re-fetches `GET /users/me` for the pre-submit staleness check each Generate/Improvise flow already did before this context existed. Follow this pattern (consume the shared context, don't add a new local `balance` state) for any future credit-spending feature.
- **`/generate_script` breaks from the card+edit-popup library pattern, but persists like a real resource**: it's a single-page multi-step flow, not CRUD-on-a-grid — `app/(app)/generate_script/page.tsx` owns one form (category/country/word-length/etc.) plus two *non-popup* result lists rendered inline: `SuggestionTopicCard.tsx` (one per researched topic, its own "+ Generate" button) and `GeneratedScriptCard.tsx` (one per generated script — numbered "Script #N" counting up from the earliest generated, shows script/word-count/character list — "None" if empty — plus Import/Improvise/Edit/Delete controls; Edit switches the card into an inline topic-input + script-textarea with Save/Cancel rather than opening a popup). The page tracks a `currentScriptTemplateId` in React state *and* `localStorage` (key `vgai_current_script_template_id`) so a reload restores the active session's form fields + topics (`GET /scripttemplates/{id}` + `.../topics`) and always re-fetches the user's full generated-script history (`GET /scripttemplates/generatedscripts`) regardless of session. A separate `activeWordLength` snapshot (set only on a successful research call, not on every keystroke) keeps the topic cards' displayed/charged credit cost in sync with what's actually stored server-side, even if the user nudges the Script Length dropdown afterward without re-researching. Only `GeneratedScriptFeedbackPopUp.tsx` (the Improvise feedback prompt), `ShowScriptTemplatesCardPopUp.tsx` (browsing saved `script_templates` to re-import into the form — has an `onDelete` callback so the page can clear its session state if the currently-active template gets deleted), and `ConformationMessagePopUp` (generated-script delete confirmation, same component `characters/page.tsx` uses) are actual portaled popups. The Target Country field is a custom searchable combobox (`countryQuery`/`countryOpen` state, filtered against `lib/countries.ts`), not a native `<select>` — a native select's dropdown/option styling is OS-controlled (ignores Tailwind dark-mode classes) and its type-ahead search has no backspace-editing, both of which were real bugs here. The "Import" button on `GeneratedScriptCard.tsx` now creates a new project (`useProjects().createProject(topic, script)`) and navigates to `/project_folder/{id}` — always a *new* project, no "import into an existing one" picker.
- **`/project_folder/{project_id}`** (`app/(app)/project_folder/[project_id]/page.tsx`): reads the dynamic segment via `useParams()` rather than the `params` prop (this Next.js version makes `params` a Promise even in Client Component pages — `useParams()` sidesteps that entirely, see `frontendweb/node_modules/next/dist/docs/.../dynamic-routes.md`). On load it fires three parallel fetches — project detail, `GET /projects/scenes/?project_id=`, `GET /projects/{id}/characters` — into local state; nothing here goes through a shared context beyond the project *list* (`ProjectsContext`) and credit balance. The script `<textarea>` autosaves on blur only (`PUT /projects/update/{id}`, partial-update payload) rather than debounced-on-keystroke, and the "Generate Scenes (Automatic)" cost readout (`ceil(wordCount / 10)`) is computed from that same local draft live as the user types, matching what the backend will actually charge once saved. Four menu buttons open `ChooseCharacterPopUp`/`ChooseStyleTemplatePopUp`/`VoiceOverControllerPopUp`/`AdvancedSettingsPopUp` (all in `components/projectfolder/`, following the same portaled-popup shell as `EditCharacterCardPopUp.tsx` etc.); each popup's `onSaved`/`onImported` callback pushes the updated `Project` straight back into the page's local state rather than triggering a re-fetch. `SceneCard.tsx` owns its own image/animation generation calls (and their `AbortController`-based Cancel buttons) internally rather than lifting that state to the page, calling `useCreditBalance().setBalance()` directly on success — same "consume the shared context, don't thread it through props" rule as the rest of the app. Its image/animation preview boxes are aspect-ratio-aware off `project.snapshot_styletemplate_video_aspect_ratio` (passed down as a prop from the page): `16:9` stacks the two previews vertically, `9:16` lays them out side by side instead, since two tall portrait previews stacked would be excessively long — both are width-capped (`previewMaxWidthClass`) rather than stretching to fill the grid column, so they read as "medium," not oversized. Clicking a generated scene image (or the `VideoMetaDataCard.tsx` thumbnail) opens the shared `ImageZoomPopUp`; clicking a generated animation opens `VideoPlayingCardPopUp.tsx` (a full-screen player with its own download button) — the small inline preview `<video>` deliberately has no `controls`/is `pointer-events-none` so a click always opens the popup instead of fighting the browser's native play/seek controls. Both cards' download buttons go through `lib/download.ts`'s `downloadAsset()`/`getFileExtension()` (fetch-as-blob + a synthetic `<a download>` click, since cross-origin URLs like Cloudinary ignore the `download` attribute and just navigate) — a per-asset `downloadStatus` map swaps the icon to a spinner then a **sticky** green checkmark (cleared only on reload, not on a timer) so the user has a lasting record of what they've already saved locally. A failed download throws `AssetUnavailableError` (carries the HTTP status) so the UI can say the host refused the file (e.g. a disabled Cloudinary account returns 401 on every asset) rather than silently redirecting to a dead page. `VideoMetaDataCard.tsx`'s thumbnail also has its own collapsible, autosave-on-blur `thumbnail_prompt` editor (toggled via a blue "Prompt" link) — independent of the card's Title/Description/Tags fields, which still require the explicit "Save Metadata" click; editing the prompt changes what the next "Regenerate Thumbnail" click actually generates (see `ProjectUpdate` schema note above).
- **All overlay popups portal to `document.body`**: `AlertMessagePopUp`, `ConformationMessagePopUp`, `ImageZoomPopUp`, `VideoPlayingCardPopUp`, `LoginModal`, both `Edit*CardPopUp`/`Generate*PopUp` components, and the Navbar's account dropdown use `createPortal`. Do the same for any new full-viewport overlay or dropdown — a `position: fixed` element nested under an ancestor with a CSS `transform` *or* `backdrop-filter` (e.g. a card's `hover:-translate-y-0.5`, or the Navbar's `backdrop-blur-md`) gets clipped to that ancestor's box instead of the viewport, since the ancestor becomes the fixed element's containing block. This bit the Navbar's account menu specifically: its outside-click backdrop was confined to the 64px navbar bar, so clicks on the page below never closed it, until the dropdown was portaled out.

## Domain model notes (see `vgaidatabase.dbml` for full schema)

- **Credits are the app's currency**: `100 credits = $1`. All AI actions (LLM, image, animation, voiceover, and one-off "miscellaneous" generations like character-sheet/style-template/script generation) are billed in credits against `users.current_credit_balance`. Script generation's cost isn't flat — it scales with the chosen `script_word_length` band (`ceil(upper_bound / WORDS_PER_CREDIT)`, `WORDS_PER_CREDIT = 30` in `viralscripttopicresearch.py` — the `ceil()` matters since 30 doesn't evenly divide every 100-word band), while topic research is a flat 5 credits regardless of inputs. Manually editing/deleting a `generated_scripts` row is free (no AI call). Project-scoped generation is billed the same currency but tracked separately (see `project_expence_tracker` bullet below): automatic scene-splitting is `ceil(script_word_count / 10)` credits (`WORDS_PER_CREDIT_AUTO` in `paidscripttoscenesplitter.py`), scene/thumbnail image generation is a flat 4 (`"base"`)/20 (`"pro"`) credits (`imagegeneration.py`), animation generation is a flat 20 (`"base"`, Wan 2.6, 5s)/40 (`"pro"`, Veo 3.1 Lite, 6s) credits (`animationgeneration.py`, `app/openrouter_video.py`). Manually editing/deleting/creating a `scenes` row is free.
- **Snapshotting pattern**: when a project imports a character or style template, the data is copied into project-scoped tables/columns (`project_characters`, `projects.snapshot_styletemplate_*`) rather than referenced live — later edits to the library item must not retroactively change existing projects. `projects.snapshot_styletemplate_*` snapshots **8** style-template fields, not just the 5 you'd expect from name/prompts/description — `image_aspect_ratio`/`video_aspect_ratio`/`scene_density` are snapshotted too (3 columns added specifically for `paidscripttoscenesplitter.py`/`imagegeneration.py`/`animationgeneration.py`, which need them at generation time and can't read them live off `style_templates` per this same snapshot rule) — keep `vgaidatabase.sql`'s `alter table` backfill block and `vgaidatabase.dbml` in sync if a 9th field is ever added. `project_characters` intentionally has **no** `character_id` FK back to `characters` (a real copy, not a reference) — but `snapshot_character_sheet_url` is a copy of the *URL string*, not a re-uploaded Cloudinary asset, so removing a `project_characters` row or deleting a project must never `delete_media()` that URL.
- **Spend history survives deletion by design**: `project_expence_tracker` stores `project_id`/`project_name` with no foreign key specifically so a project's credit-spend history remains queryable (for `/profile` usage history) after the project itself is deleted. In practice there's exactly one `project_expence_tracker` row per project (`projectcrud.py`'s `_add_project_expense()` fetches-or-creates it and increments one of `llm_credit_spent`/`image_credit_spent`/`animation_credit_spent`/`voiceover_credit_spent`), not one row per spend event — it's a running per-project total, not a transaction log.
- **`is_default` cardinality differs by table**: `characters` has no uniqueness constraint, so a user can mark multiple characters default. `style_templates` has a partial unique index (`idx_user_default_style`, `WHERE is_default = true`) enforcing at most one default per user — the route layer must unset any existing default before setting a new one (see `_clear_existing_default()` in `styletemplates/crud.py`) or the DB write fails.
